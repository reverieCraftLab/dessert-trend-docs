# 대화로 보는 의사결정 과정

실제 사이트를 만드는 결정을 내릴 때 Claude와 나눈 대화를 "질문 → Claude의 판단 → 결과" 순서로 정리한 문서입니다.
작업 방식이나 문서 형식 같은 부차적인 대화는 넣지 않았습니다.
Claude가 대화를 요약해 정리한 것이라 원문과 표현이 다를 수 있고, 최종 결정은 [decisions.md](./decisions.md)가 기준입니다.
각 결과에는 **누가 정했는지**를 함께 적었습니다.

---

## 1. 이 사이트는 누구를 위해 무엇을 해결하는가

**질문 (GT)**: 소상공인을 메인 타깃으로 생각했다. 디저트 유행이 급속도로 퍼졌다가 순식간에 식는데, 유행하기 전에 시기를 판단해 다른 가게보다 먼저 선점하게 돕는 홈페이지가 있으면 좋겠다. 두쫀쿠 때는 카다이프가 너무 비싸 품귀였고, 비싸게 산 재료가 가게에 도착했을 때는 이미 인기가 식어 있었다. 일반 고객은 서브 타깃이고, 핀터레스트 스타일로 유행하는 디저트를 보고 가게를 찾거나 저장해 두는 용도다.

**Claude의 판단 (가설로 제시)**
- 사례가 구체적이어서 줄이려는 손해가 분명하다고 보았다.
- 다만 세 가지를 짚었다. 첫째, 소상공인에게 필요한 것은 순위보다 오르는 속도일 수 있다. 순위는 이미 늦은 신호이기 때문이다. 둘째, "예측"은 검증할 수 없는 약속이라 "판단 보조"가 안전하다. 셋째, 소상공인이 이 사이트를 보고 내리는 결정이 무엇인지 알아야 시나리오를 쓸 수 있다.
- 두 타깃은 필요한 기능이 다르므로(소상공인은 시간에 따른 변화 데이터, 일반 고객은 이미지 갤러리와 가게 찾기) 어느 쪽을 MVP로 할지 따로 정해야 한다고 했다.

**결과**: 아래 2번에서 이어진다.

## 2. 타깃을 바꾸다

**질문 (GT)**: 원래 프로젝트에는 일반 유저가 메인 타깃인 게 맞다고 생각한다. 소상공인은 서브이고, 지표 화면은 나중에 추가해도 된다. 일반 유저가 모이지 않으면 예측 데이터가 유효하지 않을 것 같다.

**Claude의 판단**
- 타당하다고 보았다. 사용자가 모이기 전에는 지표를 만들 데이터가 없어서, 지표 화면을 먼저 만들면 빈 화면이 된다. 1번의 질문들은 소상공인이 주 타깃이라는 전제 위에 있었는데, 그 전제를 GT가 바꾼 것이다.
- 단, 이 논리는 지표가 사이트 안의 사용자 행동에서 나올 때 성립한다. 외부 데이터에서 나온다면 이유가 "데이터 부족"이 아니라 "범위 조절"로 바뀐다고 확인을 요청했다.
- 지표를 나중에 붙이려면 그때까지 쌓인 데이터가 필요하므로, 화면은 미뤄도 행동 기록은 처음부터 해야 한다고 제안했다.

**결과**: 주 타깃은 일반 유저, 지표 화면은 MVP에서 제외로 정했다. 결정은 GT, "행동 기록은 처음부터"라는 조건은 Claude가 제안하고 GT가 수용했다. → [D-01](./decisions.md), [D-02](./decisions.md)

## 3. 초기 데이터는 어디서 가져올 것인가

**질문 (GT)**: 행동 기록은 처음부터 하겠다. 초기에는 외부 API로 정보를 가져올 생각이고, 네이버 API를 최종적으로 생각했다. 무료 요청 횟수가 많고, 맛집과 위치를 찾을 때 네이버 지도를, 후기를 볼 때 네이버 블로그를 많이 쓰므로 한국에서는 네이버가 가장 효율적이라고 판단했다.

**Claude의 판단**
- 선택 이유는 타당하다고 보았다.
- 다만 실제로 막힐 수 있는 지점이 두 가지다. 이 사이트의 핵심이 이미지 갤러리인데 API가 주는 이미지를 내 사이트에 표시해도 되는지는 이용 약관에 달려 있다. 그리고 "무료 호출이 많다"는 인상 대신 실제 한도 숫자를 확인해야 수집 주기와 캐싱 설계의 근거가 된다.
- 네이버 API에서 어떤 정보를 가져오려는지(가게 정보, 블로그 글과 이미지, 유행 신호)에 따라 엔터티가 달라지므로 이를 질문했다.

**결과**: 초기 데이터는 네이버 API로 정했다. 결정은 GT. 이용 약관과 호출 한도 확인은 남은 과제다. → [D-03](./decisions.md)

## 4. 어떤 네이버 API를 쓸 것인가

**질문 (GT)**: 네이버 API에서 가져올 정보는 NAVER 검색 API(이미지, 블로그, 지역, 뉴스, 카페)와 Data Lab(검색어트렌드, 쇼핑인사이트)이다. 네이버 API 허브 콘솔 화면(호출 한도 포함)도 함께 공유했다.

**Claude의 판단**
- 콘솔 화면으로 호출 한도를 확인할 수 있었다. 이 내용은 D-03에 반영했다.
- 검색어트렌드는 사용자가 없어도 유행 지표를 만들 수 있는 외부 데이터라서, D-02의 이유("사용자가 모여야 지표가 유효하다")가 그대로 성립하는지 다시 확인해야 한다고 짚었다. 지표 화면을 미루는 이유가 "데이터 부족"이 아니라 "범위 조절"일 수 있다.
- API는 주어진 키워드의 데이터를 줄 뿐 새로운 디저트를 스스로 찾아주지는 않는다고 보았다. 그래서 키워드 목록을 누가 정하는지가 필요하다.
- 갤러리에 쓸 이미지를 어느 API에서 얻을 수 있는지와 그 이미지의 이용 약관을 공식 문서로 확인해야 한다고 했다.

**이어진 대화**
- GT: Data Lab의 상대 지표 문제는 더 고민해 보기로 했다. 쇼핑 인사이트로 재료 관심 변화를 보는 기능은 소상공인용으로 나중에 추가할 생각이었다고 확인했다.
- GT의 결정: 네이버가 API를 영원히 보장해 주지 않고 의존도가 너무 커지는 것이 걱정이라서, 사용자 행동을 처음부터 기록하는 쪽이 맞다고 판단했다.
- Claude: 이용 약관을 찾아봤고 처음에는 2차 자료만 확인했다.
- GT: 공식 약관 원문(NAVER API HUB, 시행 2026.09.20)을 직접 전달했다.
- Claude: 원문을 읽고 정리했다. 검색 결과의 저장·캐싱, 파생물 생성, AI 입력, 광고가 금지되고 임시 보관만 제한적으로 허용된다. 네이버가 지속성을 보증하지 않는다는 조항(10.1)도 있어서 GT의 의존도 걱정이 약관으로 확인됐다. 결과를 모아 DB에 쌓는 설계는 약관과 맞지 않으므로, 이미지와 가게 정보의 출처를 다시 정해야 한다.

**결과**: 지표용 데이터는 네이버에만 의존하지 않고 사용자 행동을 처음부터 기록하기로 했다. 결정은 GT. 약관 원문으로 이 판단이 더 단단해졌고, 갤러리 데이터의 출처는 다시 정하기로 했다. → [D-02](./decisions.md), [D-03](./decisions.md)

## 아직 답이 없는 질문

- 각 네이버 API를 어떤 용도로 쓸 것인가 (갤러리 이미지, 가게 정보, 유행 지표)
- 갤러리의 이미지와 가게 정보는 어디서 가져올 것인가 (약관상 검색 결과를 저장해 쌓는 방식은 불가, D-03)
- Data Lab 결과를 저장해도 되는가 (약관만으로는 불명확, 문의 필요)
- Data Lab의 상대 지표(조회 기간 내 최고 시점 = 100)를 지표에 어떻게 쓸 것인가 (고민 중)
- 디저트 키워드 목록은 누가 정하는가
- 사용자의 어떤 행동을 기록할 것인가
- MVP 기능은 무엇인가 (요구사항 기술서 3번 항목 작성 필요)
