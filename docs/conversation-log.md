# 대화로 보는 의사결정 과정

요구사항을 정하는 동안 Claude와 나눈 대화를 "질문 → Claude의 판단 → 결과" 순서로 정리한 문서입니다.
Claude가 대화를 요약해 정리한 것이라 원문과 표현이 다를 수 있고, 최종 결정은 [decisions.md](./decisions.md)가 기준입니다.
각 결과에는 **누가 정했는지**를 함께 적었습니다.

---

## 1. 무엇부터 할 것인가

**질문 (GT)**: 시간이 남았는데 암기 없이 생산적으로 할 만한 게 뭐가 있을까? 그러다가, 이번에 작업할 디저트 트렌드 사이트의 요구사항을 정의하는 건 어떨까? 이전에는 그냥 무작정 만들었다.

**Claude의 판단**
- 요구사항을 먼저 정하면 이후 DB 설계와 API 설계의 근거가 생긴다. "이 테이블이 왜 필요한가"에 답할 수 있게 된다.
- 순서는 목적 → 사용자와 시나리오 → 기능(우선순위) → 비기능(제약) → 데이터로 잡았다. 위에서 아래로 갈수록 앞 단계가 다음 단계의 근거가 되기 때문이다.
- 이 단계에서는 "무엇을 만들지"만 정하고, "어떻게 만들지"(ERD, API)는 섞지 않는다. 섞으면 구현하기 편한 쪽으로 요구사항이 휘어진다.

**결과**: 요구사항 기술서를 먼저 쓰기로 했다. 제안은 GT, 5단계 구성은 Claude. → [D-01](./decisions.md)

## 2. 포트폴리오에는 어떻게 남길 것인가

**질문 (GT)**: 이걸 이력서와 포트폴리오에 차근차근 채워가고 싶다.

**Claude의 판단**
- 면접에서 보는 것은 결과물보다 "왜 이렇게 했는지 설명할 수 있는가"라고 판단했다.
- 그래서 항목마다 "정한 것 / 이유 / 다른 선택지"를 짧게 남기는 결정 기록을 병행하자고 제안했다. 지금 남기지 않으면 몇 달 뒤에는 이유를 기억하지 못한다.
- 이력서에는 본인이 직접 판단하고 설명할 수 있는 것만 적어야 한다고 짚었다.

**결과**: 결정 기록(`decisions.md`)을 같이 쓰기로 했다. 제안은 Claude, 수용은 GT.

---

## 3. 문서는 어디에 쓸 것인가

**질문 (GT)**: 어디에 작성하는 게 좋을까?

**Claude의 판단**
- GitHub 저장소의 `docs/` 폴더에 마크다운으로 쓰는 안을 추천했다. 이유는 세 가지다. 이력서에 링크 하나로 코드와 문서를 함께 보여줄 수 있고, 커밋 기록에 요구사항이 바뀐 과정이 남고, 코드와 같은 흐름에서 관리돼 문서가 방치되기 어렵다.
- Notion은 초안 작성은 편하지만 변경 이력이 약하다고 비교했다. 블로그는 정리가 끝난 글을 공개하기에 좋아서, 문서가 쌓인 뒤 다듬는 순서가 낫다고 보았다.

**결과**: GitHub 마크다운으로 정했다. 제안은 Claude, 수용은 GT. → [D-02](./decisions.md)

---

## 4. 엑셀을 넣어도 되는가

**질문 (GT)**: 엑셀도 넣고 싶은데, 요즘은 그렇게 안 보려나?

**Claude의 판단**
- 엑셀은 요구사항 정의서와 추적표 용도로 현업에서 여전히 많이 쓰이므로 넣는 것 자체는 나쁘지 않다고 답했다.
- 다만 포트폴리오에서는 약점이 있다. GitHub에서 바로 열리지 않아 면접관이 지나치기 쉽고, 바이너리라서 변경 이력이 커밋에 남지 않으며, "왜"를 길게 적기 불편하다.
- 그래서 마크다운 표를 기본으로 하고, 필요하면 `.csv`를 보조로 쓰자고 제안했다. 어느 쪽이든 요구사항에 ID(FR-01 등)를 붙여 나중에 ERD와 API에 연결할 수 있게 하자고 했다.

**결과**: 확정하지 않았다. `decisions.md`의 "미확정" 항목으로 남겨 두었다.

## 5. 저장소는 어떻게 나눌 것인가

**질문 (GT)**: 저장소 이름을 `dessert-trend-docs`로 하는 게 좋을 것 같다.

**Claude의 판단**
- 이름에 `-docs`가 붙으면 문서 전용 저장소라는 뜻이라서 장단점을 먼저 짚었다. 장점은 코드가 없는 지금 단계에서 기획 문서만 깔끔하게 보인다는 점이고, 단점은 구현이 시작되면 문서와 코드가 서로 다른 저장소에 있게 된다는 점이다.
- 이름 때문에 막힐 필요는 없다고 보았다. 지금은 문서 전용으로 시작하고, 구현 단계에서 문서를 코드 저장소의 `docs/`로 옮기거나 README에서 링크로 연결하면 된다.

**결과**: 문서 전용 저장소로 시작하기로 했다. 이름은 GT가 정했다. → [D-03](./decisions.md)

## 6. AI 활용과 리뷰는 어떻게 남길 것인가

**질문 (GT)**: README에 어떤 AI로 작성 중인지 적고, 내가 작업을 마친 뒤 대화로 정리한 최종 내용에 대한 리뷰와 평가를 맨 아래에 추가해 달라.

**Claude의 판단**
- AI 활용 내용은 바로 추가했다. 내용과 결정은 작성자가 직접 하고, Claude는 순서 안내, 질문, 뼈대와 결정 기록 정리를 맡는다고 적었다.
- 리뷰는 지금 쓰지 않았다. 요구사항이 비어 있어서 평가할 내용이 없고, 내용 없이 쓰면 근거 없는 칭찬이 되기 때문이다. 완성 후에 좋은 점과 부족한 점을 함께 쓰기로 했다.

**결과**: README에 "AI 활용" 섹션을 추가하고, "AI 리뷰" 섹션은 완성 후 채우기로 했다.

## 7. 이 사이트는 누구를 위해 무엇을 해결하는가

**질문 (GT)**: 소상공인을 메인 타깃으로 생각했다. 디저트 유행이 급속도로 퍼졌다가 순식간에 식는데, 유행하기 전에 시기를 판단해 다른 가게보다 먼저 선점하게 돕는 홈페이지가 있으면 좋겠다. 두쫀쿠 때는 카다이프가 너무 비싸 품귀였고, 비싸게 산 재료가 가게에 도착했을 때는 이미 인기가 식어 있었다. 일반 고객은 서브 타깃이고, 핀터레스트 스타일로 유행하는 디저트를 보고 가게를 찾거나 저장해 두는 용도다.

**Claude의 판단 (가설로 제시)**
- 사례가 구체적이어서 줄이려는 손해가 분명하다고 보았다.
- 다만 세 가지를 짚었다. 첫째, 소상공인에게 필요한 것은 순위보다 오르는 속도일 수 있다. 순위는 이미 늦은 신호이기 때문이다. 둘째, "예측"은 검증할 수 없는 약속이라 "판단 보조"가 안전하다. 셋째, 소상공인이 이 사이트를 보고 내리는 결정이 무엇인지 알아야 시나리오를 쓸 수 있다.
- 두 타깃은 필요한 기능이 다르므로(소상공인은 시간에 따른 변화 데이터, 일반 고객은 이미지 갤러리와 가게 찾기) 어느 쪽을 MVP로 할지 따로 정해야 한다고 했다.

**결과**: 아래 8번에서 이어진다.

## 8. 타깃을 바꾸다

**질문 (GT)**: 원래 프로젝트에는 일반 유저가 메인 타깃인 게 맞다고 생각한다. 소상공인은 서브이고, 지표 화면은 나중에 추가해도 된다. 일반 유저가 모이지 않으면 예측 데이터가 유효하지 않을 것 같다.

**Claude의 판단**
- 타당하다고 보았다. 사용자가 모이기 전에는 지표를 만들 데이터가 없어서, 지표 화면을 먼저 만들면 빈 화면이 된다. 7번의 질문들은 소상공인이 주 타깃이라는 전제 위에 있었는데, 그 전제를 GT가 바꾼 것이다.
- 단, 이 논리는 지표가 사이트 안의 사용자 행동에서 나올 때 성립한다. 외부 데이터에서 나온다면 이유가 "데이터 부족"이 아니라 "범위 조절"로 바뀐다고 확인을 요청했다.
- 지표를 나중에 붙이려면 그때까지 쌓인 데이터가 필요하므로, 화면은 미뤄도 행동 기록은 처음부터 해야 한다고 제안했다.

**결과**: 주 타깃은 일반 유저, 지표 화면은 MVP에서 제외로 정했다. 결정은 GT, "행동 기록은 처음부터"라는 조건은 Claude가 제안하고 GT가 수용했다. → [D-04](./decisions.md), [D-05](./decisions.md)

## 9. 초기 데이터는 어디서 가져올 것인가

**질문 (GT)**: 행동 기록은 처음부터 하겠다. 초기에는 외부 API로 정보를 가져올 생각이고, 네이버 API를 최종적으로 생각했다. 무료 요청 횟수가 많고, 맛집과 위치를 찾을 때 네이버 지도를, 후기를 볼 때 네이버 블로그를 많이 쓰므로 한국에서는 네이버가 가장 효율적이라고 판단했다.

**Claude의 판단**
- 선택 이유는 타당하다고 보았다.
- 다만 실제로 막힐 수 있는 지점이 두 가지다. 이 사이트의 핵심이 이미지 갤러리인데 API가 주는 이미지를 내 사이트에 표시해도 되는지는 이용 약관에 달려 있다. 그리고 "무료 호출이 많다"는 인상 대신 실제 한도 숫자를 확인해야 수집 주기와 캐싱 설계의 근거가 된다.
- 네이버 API에서 어떤 정보를 가져오려는지(가게 정보, 블로그 글과 이미지, 유행 신호)에 따라 엔터티가 달라지므로 이를 질문했다.

**결과**: 초기 데이터는 네이버 API로 정했다. 결정은 GT. 이용 약관과 호출 한도 확인은 남은 과제다. → [D-06](./decisions.md)
