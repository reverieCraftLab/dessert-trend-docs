# 대화로 보는 의사결정 과정

실제 사이트를 만드는 결정을 내릴 때 Claude와 나눈 대화를 "질문 → Claude의 판단 → 결과" 순서로 정리한 문서입니다.
작업 방식이나 문서 형식 같은 부차적인 대화는 넣지 않았습니다.
Claude가 대화를 요약해 정리한 것이라 원문과 표현이 다를 수 있고, 최종 결정은 [decisions.md](./decisions.md)가 기준입니다.
각 결과에는 **누가 정했는지**를 함께 적었습니다.

---

## 1. 이 사이트는 누구를 위해 무엇을 해결하는가

**질문 (GT)**: 소상공인을 메인 타깃으로 생각했다. 디저트 유행이 급속도로 퍼졌다가 순식간에 식는데, 유행하기 전에 시기를 판단해 다른 가게보다 먼저 선점하게 돕는 홈페이지가 있으면 좋겠다. 두쫀쿠 때는 카다이프가 너무 비싸 품귀였고, 비싸게 산 재료가 가게에 도착했을 때는 이미 인기가 식어 있었다. 일반 고객은 서브 타깃이고, 핀터레스트 스타일로 유행하는 디저트를 보고 가게를 찾거나 저장해 두는 용도다.

**Claude의 판단 (가설로 제시)**
- 사례가 구체적이어서 줄이려는 손해가 분명하다고 보았다.
- 다만 세 가지를 짚었다. 첫째, 소상공인에게 필요한 것은 순위보다 오르는 속도일 수 있다. 순위는 이미 늦은 신호이기 때문이다. 둘째, "예측"은 검증할 수 없는 약속이라 "판단 보조"가 안전하다. 셋째, 소상공인이 이 사이트를 보고 내리는 결정이 무엇인지 알아야 시나리오를 쓸 수 있다.
- 두 타깃은 필요한 기능이 다르므로(소상공인은 시간에 따른 변화 데이터, 일반 고객은 이미지 갤러리와 가게 찾기) 어느 쪽을 MVP로 할지 따로 정해야 한다고 했다.

**결과**: 아래 2번에서 이어진다.

## 2. 타깃을 바꾸다

**질문 (GT)**: 원래 프로젝트에는 일반 유저가 메인 타깃인 게 맞다고 생각한다. 소상공인은 서브이고, 지표 화면은 나중에 추가해도 된다. 일반 유저가 모이지 않으면 예측 데이터가 유효하지 않을 것 같다.

**Claude의 판단**
- 타당하다고 보았다. 사용자가 모이기 전에는 지표를 만들 데이터가 없어서, 지표 화면을 먼저 만들면 빈 화면이 된다. 1번의 질문들은 소상공인이 주 타깃이라는 전제 위에 있었는데, 그 전제를 GT가 바꾼 것이다.
- 단, 이 논리는 지표가 사이트 안의 사용자 행동에서 나올 때 성립한다. 외부 데이터에서 나온다면 이유가 "데이터 부족"이 아니라 "범위 조절"로 바뀐다고 확인을 요청했다.
- 지표를 나중에 붙이려면 그때까지 쌓인 데이터가 필요하므로, 화면은 미뤄도 행동 기록은 처음부터 해야 한다고 제안했다.

**결과**: 주 타깃은 일반 유저, 지표 화면은 MVP에서 제외로 정했다. 결정은 GT, "행동 기록은 처음부터"라는 조건은 Claude가 제안하고 GT가 수용했다. → [D-01](./decisions.md), [D-02](./decisions.md)

## 3. 초기 데이터는 어디서 가져올 것인가

**질문 (GT)**: 행동 기록은 처음부터 하겠다. 초기에는 외부 API로 정보를 가져올 생각이고, 네이버 API를 최종적으로 생각했다. 무료 요청 횟수가 많고, 맛집과 위치를 찾을 때 네이버 지도를, 후기를 볼 때 네이버 블로그를 많이 쓰므로 한국에서는 네이버가 가장 효율적이라고 판단했다.

**Claude의 판단**
- 선택 이유는 타당하다고 보았다.
- 다만 실제로 막힐 수 있는 지점이 두 가지다. 이 사이트의 핵심이 이미지 갤러리인데 API가 주는 이미지를 내 사이트에 표시해도 되는지는 이용 약관에 달려 있다. 그리고 "무료 호출이 많다"는 인상 대신 실제 한도 숫자를 확인해야 수집 주기와 캐싱 설계의 근거가 된다.
- 네이버 API에서 어떤 정보를 가져오려는지(가게 정보, 블로그 글과 이미지, 유행 신호)에 따라 엔터티가 달라지므로 이를 질문했다.

**결과**: 초기 데이터는 네이버 API로 정했다. 결정은 GT. 이용 약관과 호출 한도 확인은 남은 과제다. → [D-03](./decisions.md)

## 4. 어떤 네이버 API를 쓸 것인가

**질문 (GT)**: 네이버 API에서 가져올 정보는 NAVER 검색 API(이미지, 블로그, 지역, 뉴스, 카페)와 Data Lab(검색어트렌드, 쇼핑인사이트)이다. 네이버 API 허브 콘솔 화면(호출 한도 포함)도 함께 공유했다.

**Claude의 판단**
- 콘솔 화면으로 호출 한도를 확인할 수 있었다. 이 내용은 D-03에 반영했다.
- 검색어트렌드는 사용자가 없어도 유행 지표를 만들 수 있는 외부 데이터라서, D-02의 이유("사용자가 모여야 지표가 유효하다")가 그대로 성립하는지 다시 확인해야 한다고 짚었다. 지표 화면을 미루는 이유가 "데이터 부족"이 아니라 "범위 조절"일 수 있다.
- API는 주어진 키워드의 데이터를 줄 뿐 새로운 디저트를 스스로 찾아주지는 않는다고 보았다. 그래서 키워드 목록을 누가 정하는지가 필요하다.
- 갤러리에 쓸 이미지를 어느 API에서 얻을 수 있는지와 그 이미지의 이용 약관을 공식 문서로 확인해야 한다고 했다.

**이어진 대화**
- GT: Data Lab의 상대 지표 문제는 더 고민해 보기로 했다. 쇼핑 인사이트로 재료 관심 변화를 보는 기능은 소상공인용으로 나중에 추가할 생각이었다고 확인했다.
- GT의 결정: 네이버가 API를 영원히 보장해 주지 않고 의존도가 너무 커지는 것이 걱정이라서, 사용자 행동을 처음부터 기록하는 쪽이 맞다고 판단했다.
- Claude: 이용 약관을 찾아봤고 처음에는 2차 자료만 확인했다.
- GT: 공식 약관 원문(NAVER API HUB, 시행 2026.09.20)을 직접 전달했다.
- Claude: 원문을 읽고 정리했다. 검색 결과의 저장·캐싱, 파생물 생성, AI 입력, 광고가 금지되고 임시 보관만 제한적으로 허용된다. 네이버가 지속성을 보증하지 않는다는 조항(10.1)도 있어서 GT의 의존도 걱정이 약관으로 확인됐다. 결과를 모아 DB에 쌓는 설계는 약관과 맞지 않으므로, 이미지와 가게 정보의 출처를 다시 정해야 한다.

- GT: 네이버에서 최근 많이 검색된 디저트 이름을 가져오고, 그 이름을 기준으로 이미지를 끌어와 보여주려 했다고 설명했다. 키워드 목록을 직접 관리할 생각은 아니었다.
- Claude: Data Lab 공식 문서를 확인했다. 검색어 트렌드와 쇼핑 인사이트는 요청에 넣은 키워드의 추이(상대값)만 주고, 인기 검색어나 순위를 주는 기능은 문서에 없다. 그래서 뜨는 디저트 이름을 네이버에서 가져오는 방식은 불가능하고, 후보 이름은 다른 곳에서 얻어야 한다. 블로그 글에서 이름을 뽑는 방식은 검색 API 약관(1.1, 1.3)에 걸려서 권하지 않았다.

**결과**: 지표용 데이터는 네이버에만 의존하지 않고 사용자 행동을 처음부터 기록하기로 했다. 결정은 GT. 약관 원문으로 이 판단이 더 단단해졌고, 갤러리 데이터의 출처는 다시 정하기로 했다. → [D-02](./decisions.md), [D-03](./decisions.md)

## 5. 로그인은 필요한가

**질문 (Claude → GT)**: 시나리오를 정리하다가, 저장 기능(SC-03)을 쓰려면 회원가입이나 로그인이 필요한지 물었다.

**GT의 답**: 처음에는 로그인 없이 동작하고, 기기를 바꾸거나 삭제하면 히스토리가 지워지는 것으로 적용한다. 기기가 바뀌어도 이어지게 하는 건 회원가입·로그인이 필요한 부분이라 나중에 추가한다.

**Claude의 판단**
- 로그인 없는 구조는 가입 문턱이 없지만, 사용자 단위 행동 기록을 쌓기 어렵다. 그래서 서버에 쌓는 행동 기록(D-02)을 익명 기기 ID로 묶을지 정해야 한다고 짚었다.
- 기기에 저장하는 데이터가 네이버 API 결과를 포함하면 약관의 기기 보관 제한(24시간)과 부딪힐 수 있어서, 자체 디저트 식별자만 저장하는 쪽이 안전하다고 보았다.

**결과**: 처음에는 로그인 없이 기기에 저장하고, 로그인은 나중에 추가하기로 했다. 결정은 GT. → [D-04](./decisions.md)

---

## 6. 행동 기록을 기기 ID로 묶을 것인가

**질문 (Claude → GT)**: 로그인이 없으면 서버 행동 기록을 사용자 단위로 묶기 어렵다. 같은 사람이 같은 디저트를 여러 번 눌러도 숫자가 부풀 수 있어서, 익명 기기 ID로 묶을지 물었다.

**GT의 답**: 묶는다. 나중에 모바일 앱으로도 만들 생각이기 때문이다.

**Claude의 판단**
- GT의 이유에 더해, 앱에서도 설치 단위 ID로 같은 방식을 쓸 수 있다고 보았다.
- 나중에 로그인을 추가하면 이 ID와 계정을 연결해 그동안 쌓은 기록을 이어 붙일 수 있다. ID 없이 기록하면 이 연결이 불가능하다.
- 대신 이 ID와 행동 기록이 개인정보 처리 대상이 될 수 있어 안내와 보관 기준이 필요하다.

**결과**: 행동 기록은 익명 기기 ID로 묶기로 했다. 결정은 GT. → [D-05](./decisions.md)

## 7. 이미지를 누르면 무엇을 보여줄 것인가

**질문 (GT)**: 처음에는 이미지를 누르면 해당 블로그로 이동하는 방식을 생각했다. 블로그 글을 가공·저장해서 그 이미지를 쓴다는 전제였는데, 약관을 보니 맞지 않는다. 대신 이미지를 누르면 지도를 열어 그 디저트를 현재 위치 기준 주변 가게에서 검색하고, 위치 권한이 없으면 지정한 기본 위치에서 시작해 지도를 옮긴 뒤 다시 조회하는 방식은 어떤가?

**Claude의 판단**
- 블로그 내용이 필요 없고 요청 때마다 호출해 보여주면 되므로 저장 문제가 사라진다. 다만 갤러리에 보일 이미지의 출처는 여전히 열려 있다고 짚었다.
- 네이버 지역 검색 API는 요청당 최대 5개이고 좌표·반경 검색이 없다. 카카오 로컬 API는 좌표·반경과 지도 영역 검색을 지원하지만 약관은 확인하지 못했다.
- 이동 후 재검색 흐름은 표준 패턴이지만, 드래그마다 검색하지 말고 버튼으로 하기를 권했다. 위치는 서버로 보내지 않기를 권했다.
- 가장 큰 미검증 가정은 메뉴 이름으로 장소 검색이 되는가였다.

**GT의 답**
- 네이버 지도 앱에서는 음식 이름으로 검색하면 가게가 조회되었다. 이것이 Claude가 아는 것과 다른 것인지, 앱이 제공하는 기능인지 물었다.
- 위치는 브라우저에서만 쓰고 서버에는 두지 않는다. "이 위치에서 검색" 버튼을 쓴다.
- 카카오 약관 확인은 보류한다. 갤러리 이미지 출처는 네이버 문의 답변을 기다린다.

**Claude의 확인**
- 네이버 클라우드 지도 서비스에는 장소 검색 API가 없다(지도 표시, 주소 검색, 경로뿐). 네이버 지도 앱의 메뉴 검색을 API로 쓸 방법은 문서에서 찾지 못했다.
- 앱에서 되는 것과 API에서 되는 것은 별개라서, 지역 검색 API로 직접 테스트해야 한다.
- 카카오 약관을 확인했다. 카카오도 응답 결과의 저장을 허용하지 않고 실시간 호출만 가능하다. 장소 검색 무료 쿼터는 일 100,000건으로 네이버 검색(일 25,000건)보다 크고, 위치·반경 검색을 지원한다. 장소 ID만 저장하는 방식은 허용 가능하다는 포럼 답변이 있었지만 공식 확인은 아니다.
- 네이버 지도 가이드(Maps 개요, 지도 앱 연동 URL Scheme)를 읽었다. Maps API 목록(Web Dynamic Map, Mobile SDK, Static Map, Directions, Geocoding, Reverse Geocoding)에 메뉴나 장소 검색은 없다. 다만 네이버 지도 앱 URL Scheme의 통합 검색(`nmap://search?query=검색어`)은 앱의 검색을 그대로 열어 준다. 앱이 설치된 기기에서만 동작하고, 검색 액션에는 위치 파라미터가 없으며, 이 호출로 메뉴 이름 검색이 되는지는 직접 확인하지 못했다.

**결과**: 위치 정보 처리와 버튼 방식은 정했다. 지도 흐름 자체는 테스트 결과 후 확정한다. 결정은 GT. → [D-06](./decisions.md)

## 8. 네이버 문의 답변

**질문 (GT)**: 약관 해석이 갈리는 4가지를 네이버 클라우드 플랫폼에 문의했다. (1) 결과를 저장하지 않고 계산한 집계 수치만 보관해도 되는가, (2) Data Lab의 ratio를 저장해 추이·순위로 보여줘도 되는가, (3) 사용자 저장 기능에서 항목 URL만 저장하고 표시할 때마다 재호출해도 되는가, (4) 이미지 검색 결과를 그리드로 나열해도 되는가.

**답변 요약**
- (1) 계산한 뒤 보관하는 것이므로 가공·파생물의 저장에 해당한다. 안 된다.
- (2)·(3) 약관 7.3에 따라 DB나 AI에 데이터를 저장하는 것은 금지다. 두 문의를 묶어 답했고, 저장 기간과 출처 표기는 답에 없다.
- (4) 가공 없이 노출하는 요건에 맞는다.
- 설계 시 확인하라고 안내한 조항: 7.2③, 7.3③·④·⑤·⑫, 8.1·8.2.

**Claude의 판단**
- 문의 번호와 답변 번호를 맞춰 보는 과정에서, 문의 2·3의 답이 한 줄로 합쳐져 있어 (b)·(c)와 "URL만 저장" 방식은 답을 받지 못했다고 구분해서 기록했다.
- 네이버 결과를 모아 순위나 지표를 만드는 길은 공식 답변으로 막혔다. 따라서 시간이 지나며 쌓이는 데이터는 우리 사용자의 행동 기록뿐이고, D-02·D-05의 판단이 확인되었다.
- 사용자 저장 기능에 네이버 URL을 쓸 수 없으므로, 자체 식별자로 저장해야 한다. 이때 디저트 후보 이름의 출처가 더 중요해진다.
- 처음 정리에서 빠졌던 7.2③(이용 대가 금지), 7.3⑤(다수 클라이언트 ID 금지), 7.3⑫(주기적·지속적 접속 금지), 8.1·8.2(권리 귀속)는 원문을 확인해 D-03에 정리했다. 유료화는 네이버 데이터 기반으로는 불가하고, 호출은 사용자 요청 때에 맞추는 것이 안전하며, 갤러리 이미지는 원 저작자의 것을 빌려 보여주는 것으로 본다. 이 영향은 Claude의 해석이고 네이버 확인은 받지 않았다.

**결과**: 갤러리 이미지는 요청 때마다 호출해 가공 없이 보여주는 방식이 가능하다. 네이버 결과의 저장과 집계는 쓰지 않는다. → [D-03](./decisions.md)

## 9. 홈페이지 방향 변경: 실시간 수집 대신 고른 목록과 사용자 검색

**질문 (GT)**: 이 페이지의 가장 큰 메리트는 "실시간 유행을 놓치지 않는 것" 하나이고, 나머지는 사용자가 쓰면서 파생된다. 그러니 데이터를 어떻게 수집하는지가 가장 중요하다. 디저트 후보를 자동으로 수집하는 방향이다.

**Claude의 판단**
- 네이버와 카카오는 저장·가공이 금지라 "보여주기용"이다. 구글 트렌드 API(알파)는 신청이 필요하고 약관을 확인하지 못했다. 유튜브는 파생 지표와 데이터 결합이 제한되고, 인스타그램은 해시태그를 입력해야 하며 7일에 30개까지다.
- 거의 모든 공식 API가 "이름을 넣으면 추이를 주는" 구조라서, 새로 뜨는 이름을 발견하는 기능은 찾지 못했다. 발견 단계가 비어 있고 검증 단계(Data Lab)는 가능하다.
- 남은 길(네이버 제휴 문의, 유료 데이터, 사용자 행동 신호, 반자동)과 각각의 트레이드오프를 제시했고, 핵심 가치의 실현 가능성이 미해결이라고 밝혔다.

**GT의 답**
- 실시간 수집은 어려우니 방향을 바꾼다. 홈에는 요즘 유행하는 디저트를 몇 개 두고 랭킹은 보여주지 않는다. 사용자가 검색하면 네이버 이미지 검색 API로 이미지를 가져와 사용자에게 제공한다.
- 실시간 유행은 나중에 사용자들이 디저트를 검색하면서 자연스럽게 쌓일 것이다.
- 검색 한도가 걱정이다. 사용자가 늘면 멈출 텐데, 레디스에 저장하는 것도 안 되는 것 아니냐고 물었다.
- 요금과 광고 수익은 지금은 필요 없다.

**Claude의 확인**
- 이 방향은 문의 4번에서 허용된 "가공 없는 실시간 노출"만 쓰고, 사용자의 검색어는 우리 데이터라서 저장해도 약관과 충돌하지 않는다. 저장 기능은 디저트 이름 저장으로 풀린다.
- 레디스 캐시는 특약 1.4가 허용하는 보관(기기 24시간, 서버 최대 21일, 이력 조회 목적)에 공유 캐시가 포함되는지 불분명해서 안 된다고 단정할 수 없다. 문의가 필요하다.

**결과**: 방향을 바꾸기로 했다. 결정은 GT. → [D-07](./decisions.md)

## 10. 홈 구성과 MVP 범위

**질문 (GT)**: 요즘 유행하는 디저트를 미리 DB에 넣어 두고, 접속하면 랜덤으로 뜨게 하고 싶다. 이미지는 디저트를 섞어서 핀터레스트처럼 배치하고 싶다. 약관이 모호하니 마카롱 3개, 티라미수 3개처럼 열로 나누어 이어서 보여주면 되는 것 아닌가?

**Claude의 판단**
- 이미지는 저장할 수 없어서 디저트 카드마다 이미지를 가져오면 호출이 크게 늘어난다. 디저트 1~3개의 갤러리를 한 번에 보여주면 호출 수가 줄어든다.
- 약관(특약 1.2)은 결과의 앞·뒤·중간에 다른 내용을 넣는 것을 금지한다. 디저트를 한 격자에 섞으면 이 문구에 걸릴 수 있어, 디저트별로 묶어서 보여주는 것을 권했다.
- GT가 제안한 열 배치는 디저트마다 결과가 끊기지 않은 한 줄이 되므로 위험이 낮다고 보았다. 다만 한 디저트 안의 순서는 API 순서를 유지해야 하고, 약관 해석은 네이버 확인이 아니다.
- 기능 요구사항 초안(FR-01~09)을 만들어 확인을 받았다.

**GT의 답**
- 열 배치로 가고, 관리 화면은 만들되 후순위로 한다.
- 여행지 디저트 찾기는 위치 기반 조회와 지도 이동으로 되므로 별도 기능은 필요 없다.
- 저장 기능은 추후 논의 및 개발로 미룬다.

**결과**: MVP 범위를 정리했다. → [요구사항 3장](./01-requirements.md), [D-07](./decisions.md)

## 11. 어떤 행동을 기록할 것인가 (개인정보)

**질문 (GT)**: 익명 기기 ID를 서버에 쌓는 것이 개인정보 처리와 어떻게 이어지는지 다시 정리하고 싶다. (저장을 미룬 이유로 든 "약관·로그인"은 내 오해였다.)

**Claude의 판단**
- 개인정보 보호법 제2조는 다른 정보와 쉽게 결합해 알아볼 수 있으면 개인정보에 포함한다고 한다(법률 자문 아님).
- 익명 기기 ID는 단독으로는 개인을 알아보기 어렵다. 하지만 나중에 로그인과 연결하면 기존 기록이 계정과 결합되고, 서버 로그의 IP와 합칠 수 있으면 식별 가능성이 커진다. 검색어는 자유 입력이라 개인정보가 섞일 수 있다.
- 그래서 기록 항목을 줄이고(기기 ID, 검색어, 시각), 기기 ID는 브라우저에서 만들고, 로그인 연결 전에 동의를 받고, 안내문을 게시하는 6가지를 제안했다.

**GT의 답**
- 기록하는 행동은 사용자가 검색한 디저트 이름만으로 한다.
- 제안한 6가지 중 맞지 않는 것은 없다.
- 보관 기간은 일단 미정으로 둔다.
- 저장 기능은 추후 논의 및 개발한다.

**결과**: 기록 항목과 개인정보 처리 방침을 정했다. → [D-05](./decisions.md), [요구사항 NFR-02, NFR-03](./01-requirements.md)

## 12. 비기능 요구사항과 데이터 테이블 정하기

**질문 (GT)**: 요구사항에 비기능 항목(NFR)을 하나씩 정하고, 디저트와 행동 기록 테이블을 설계하자. 테스트가 필요한 것은 시나리오를 받아 직접 확인하겠다.

**확인한 것 (직접 호출)**
- 검색 한도는 이미지와 지역 검색이 합산이다. 요청 1건은 `display` 값과 무관하게 1회이고, 0건과 잘못된 요청도 1회다. 한도를 넘기면 HTTP 429(일별 사용량 한도 초과)가 오고, 거절된 요청은 세지 않는다.
- 네이버 응답 시간은 이미지 검색(100장) 0.24~0.26초, 지역 검색 0.14초다.

**주고받은 판단**
- 호출 한도, 약관 준수, 키 보안, 서버 구성, 응답 시간(2.5초), 실패 처리, 모바일 대응을 NFR-04~10으로 정했다.
- 집에 남는 컴퓨터를 서버로 쓰는 안은 외부 접속과 안정성 문제로 이번에는 보류하고 EC2를 유지했다(GT가 나중에 다시 생각하기로 함).
- 한도 소진 시 카카오 이미지 검색으로 대체하는 안은 사용자가 늘어난 뒤로 미뤘다(D-03).
- 지도 중심 좌표를 지역명으로 바꾸는 방식은 MVP 화면을 만든 뒤 판단하기로 했다(D-06).
- 디저트 테이블은 처음에 화면 이름과 검색어를 나눠 제안했으나, GT가 둘이 같은 단어라고 해서 하나(`keyword`)로 합쳤다(D-08).
- 행동 기록 테이블은 네 컬럼으로 하고, 원본은 오래 두지 않으며 나중에 통계 테이블에 모으기로 했다(D-09).
- 기본 지도 위치는 강남역으로 정했다(D-10).
- 시작용 디저트 10개를 GT가 골랐고, 이미지 검색 결과를 제목으로 확인한 뒤 화면에서 조정하기로 했다(D-12).
- 범위 확장은 동·역 → 구 → 시 순서로 자동으로 하고, 사용자에게 알리지 않는다. 한도 소진 문구는 사용자를 본 뒤 추가한다(D-11).

**결과**: → [요구사항 NFR-04~10, 5.1, 5.2](./01-requirements.md), [D-08~D-12](./decisions.md)

- 갤러리에 보일 이미지는 어디서 가져올 것인가 (이미지 검색 결과를 가공 없이 실시간으로 보여주는 것은 가능, 저장은 불가. D-03)
- 가게 검색은 어디서 하고, 메뉴 이름으로 검색이 되는가 (네이버·카카오 직접 호출 결과는 D-06에 기록. 메뉴 단위 검색은 어려워 보이지만 실제 판매 여부는 미확인)
- 이미지를 누르면 네이버 지도 앱 검색으로 연결할 것인가, 자체 지도 화면을 만들 것인가 (D-06)
- Data Lab은 저장 없이 실시간 조회로만 쓸 것인가 (저장은 금지로 답변받음)
- Data Lab의 상대 지표(조회 기간 내 최고 시점 = 100)를 지표에 어떻게 쓸 것인가 (고민 중)
- 행동 기록의 보관 기간과 안내문 문구 (D-05)
- 행동 기록 원본의 보관 기간과 통계 테이블의 집계 기준 (D-09)
