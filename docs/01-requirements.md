# 요구사항 기술서

> 핀터레스트 스타일 디저트 트렌드 사이트의 요구사항 정의 문서입니다.
> 상태: 작성 중 (뼈대만 있음). 결정의 근거는 [decisions.md](./decisions.md)에 남깁니다.

이 문서는 "무엇을 만들지"만 정합니다. "어떻게 만들지"(ERD, API, 구조)는 다음 단계 문서에서 다룹니다.

## 1. 목적

> 누가, 무엇을 위해 쓰는 사이트인가를 한 문장으로 적는다.

요즘 유행하거나 예쁜 디저트를 핀터레스트 스타일 이미지로 한눈에 보고, 가게를 찾거나 저장해 두었다가 생각날 때나 여행 중에 찾아가 볼 수 있게 하는 사이트.

- **주 타깃**: 일반 유저 ([D-01](./decisions.md))
- **서브 타깃**: 소상공인. 유행이 빨리 식어서, 비싸게 구한 재료가 도착했을 때는 이미 인기가 사라지는 손해를 줄이는 것이 배경이다. 이를 위한 유행 시점 지표는 사용자가 모인 뒤 추가하는 확장 기능으로 둔다. ([D-02](./decisions.md))

## 2. 사용자 및 시나리오

> 사용자 종류별로, 그 사람이 이 사이트에서 하는 일을 3~5개씩 적는다. 기능은 여기서 나온다.

| ID | 사용자 | 시나리오 |
|---|---|---|
| SC-01 | 일반 유저 | 요즘 유행하거나 예쁜 디저트를 이미지로 한눈에 훑어본다. |
| SC-02 | 일반 유저 | 마음에 드는 디저트를 파는 가게를 찾는다. |
| SC-03 | 일반 유저 | 디저트나 가게를 저장해 두었다가 생각날 때 다시 꺼내 본다. (MVP 후순위, FR-07) |
| SC-04 | 일반 유저 | 여행지에서 그 지역의 다양한 디저트를 찾아본다. (별도 기능 없이 FR-04, FR-05로 해결: 현재 위치에서 보거나 지도를 직접 옮김) |
| SC-05 | 소상공인(서브) | 어떤 디저트가 뜨는지 보고 재료 구매나 메뉴 도입 시점을 판단한다. (MVP 제외, [D-02](./decisions.md)) |

**로그인**: 처음에는 회원가입·로그인 없이 사용한다. SC-03의 저장 기록은 사용자의 기기에 보관하고, 기기를 바꾸거나 데이터를 삭제하면 사라진다. 이 점은 서비스 안에서 사용자에게 알린다. 기기가 바뀌어도 기록이 이어지게 하는 것은 회원가입·로그인이 필요한 기능이라 나중에 추가한다. ([D-04](./decisions.md))

## 3. 기능 요구사항

> 시나리오를 기능으로 바꾸고 우선순위를 나눈다. 우선순위: 필수(MVP) / 있으면 좋음 / 나중에

| ID | 요구사항 | 우선순위 | 근거(시나리오) |
|---|---|---|---|
| FR-01 | 홈에서 DB에 미리 넣어둔 노출 중인 디저트 중 1~3개를 랜덤으로 뽑아, 디저트마다 열(구역)로 이미지 갤러리를 보여준다. | 필수(MVP) | SC-01, [D-07](./decisions.md) |
| FR-02 | 이미지는 네이버 이미지 검색을 요청 시점에 호출해 보여준다. 한 디저트 안은 API 순서를 유지하고 다른 디저트와 섞지 않으며, 출처·원본 링크·네이버 표기를 붙인다. 스크롤하면 같은 디저트의 이미지를 이어서 불러온다. | 필수 | [D-03](./decisions.md), [D-07](./decisions.md) |
| FR-03 | 사용자가 디저트 이름을 검색하면 같은 방식으로 이미지 갤러리를 보여준다. | 필수 | SC-01 |
| FR-04 | 이미지를 누르면 지도 화면으로 이동해 그 디저트를 파는 가게를 마커와 카드로 보여준다. 위치 권한이 있으면 현재 위치, 없으면 지정한 기본 위치에서 시작한다. | 필수 | SC-02, SC-04, [D-06](./decisions.md) |
| FR-05 | 지도를 옮긴 뒤 "이 위치에서 검색" 버튼을 누르면 지도 중심 기준으로 가게를 다시 조회한다. | 필수 | SC-02, SC-04, [D-06](./decisions.md) |
| FR-06 | 가게 결과가 없으면 지역을 넓혀 다시 조회하고, 화면에 그 사실을 알린다. 넓히는 단계와 문구는 미정이다. | 필수(정책 미정) | [D-06](./decisions.md) |
| FR-07 | 디저트 이름을 저장하고 저장 목록에서 다시 꺼내 본다. 추후 논의 및 개발한다(MVP 제외). | 나중에 | SC-03, [D-04](./decisions.md) |
| FR-08 | 사용자가 검색한 디저트 이름을 익명 기기 ID와 함께 기록한다. 그 밖의 행동은 기록하지 않고, 위치 좌표도 넣지 않는다. | 필수 | [D-02](./decisions.md), [D-05](./decisions.md), NFR-01 |
| FR-09 | 운영자가 홈에 올릴 디저트(표시 이름, 검색어, 노출 여부)를 관리하는 화면. MVP에서는 DB에 직접 입력한다. | 나중에 | [D-07](./decisions.md) |

MVP에서 제외(나중에 추가):
- 소상공인용 유행 지표 화면 ([D-02](./decisions.md))
- 디저트 저장 기능 (FR-07)
- 디저트를 한 격자에 섞어 보여주는 배치 (약관 확인 후)
- 디저트 관리 화면 (FR-09)
- 회원가입·로그인과 기기 간 기록 동기화 ([D-04](./decisions.md))

## 4. 비기능 요구사항

> 이미 정해진 제약과 품질 기준을 적는다. 예: 서버 사양, DB 플랜, 응답 속도 기대치.

| ID | 요구사항 | 근거 |
|---|---|---|
| NFR-01 | 사용자의 위치 정보는 브라우저에서만 사용하고 서버로 전송하거나 저장하지 않는다. 행동 기록에도 좌표를 넣지 않는다. | 위치는 민감한 정보라 서버에 두면 동의·안내 등의 부담이 커진다. ([D-06](./decisions.md)) |
| NFR-02 | 행동 기록에는 기기 ID, 검색한 디저트 이름, 시각만 넣는다. 검색어는 길이를 제한하고 개인정보로 보이는 입력(예: 숫자만 있는 입력)은 저장하지 않는 처리를 검토한다. 기록하는 내용과 지우는 방법을 서비스 안에서 안내한다. | 기기 ID와 기록이 다른 정보와 쉽게 결합하면 개인정보가 될 수 있어 수집 항목을 줄인다. 법률 자문은 아니다. ([D-05](./decisions.md)) |
| NFR-03 | 나중에 로그인을 붙일 때는 기기 ID와 계정을 연결하기 전에 사용자의 동의를 받는다. | 연결하는 순간 기존 기록이 계정과 결합되기 때문이다. ([D-05](./decisions.md)) |
| NFR-04 | 네이버 검색 API의 일 한도 25,000회(이미지·지역 검색 합산)를 전제로 설계한다. 서버는 검색어와 `display`, `start` 값을 네이버로 보내기 전에 검증한다. 429를 받으면 재시도하지 않고 한도 소진을 안내한다. 이미지는 한 번에 최대 개수(100장)를 받아 화면에서 나눠 보여준다. 범위 확장(FR-06)은 단계 수에 상한을 두며, 값은 정책 결정 시 정한다. | 측정 결과(2026-10-21): 요청 1건은 `display`와 무관하게 1회, 0건·잘못된 요청도 1회, 한도 초과로 거절된 요청(429)은 미집계, 이미지와 지역 검색은 한도 공유. 방문당 호출을 2~4회로 가정하면 하루 약 6,000~12,000명이 한계이며 이 숫자는 추정이다. ([D-03](./decisions.md)) |
| NFR-05 | 네이버 검색 API 결과는 이용약관에 맞게 표시한다. (1) 가공하지 않고 API가 준 순서대로 보여주며, 결과 사이에 다른 내용을 끼우거나 순서를 바꾸지 않는다. (2) 출처, 원본 링크, 네이버 표기를 함께 보여준다. (3) 서버나 DB에 저장하지 않고, 브라우저에는 24시간까지만 임시로 둔다. (6) 자동·주기적 호출로 서버에 과부하를 주지 않는다. | 약관(2026.09.20 시행) 특약 1.1~1.4, 7.2③, 7.3③④⑤⑥⑫에 따른다. 약관 해석이며 법률 자문은 아니다. 확인된 사항: 사용 중인 앱 `tc-collector`는 다른 프로젝트에 쓰이지 않고, 외부 공개 API를 열 계획은 없다. 서버 공유 캐시가 특약 1.4(서버 21일 이내 보관)에 해당하는지 불명확해 쓰지 않으며, 문의 여부는 미정이다. | NFR-08 | 홈 화면 접속 후 첫 이미지가 보이기까지 2.5초 이내를 목표로 한다. | NFR-09 | 네이버 API가 실패하거나 한도를 초과(429)하면 화면 전체를 오류로 바꾸지 않고 해당 영역에 안내 문구를 보여준다. 디저트 이름 목록과 검색창은 계속 쓸 수 있게 한다. 같은 호출을 자동으로 재시도하지 않고 사용자가 직접 다시 시도하게 한다. 결과가 0건이면 FR-06의 범위 확장을 적용하고, 그래도 0건이면 결과가 없다고 안내한다. 행동 기록(FR-08)은 네이버 호출의 성공 여부와 무관하게 저장한다. | 이미지를 저장하지 않으므로(D-03) 네이버가 안 되면 보여줄 이미지가 없다. 화면 전체를 오류로 만들면 사이트가 죽은 것처럼 보이므로 영역별로 안내하고 나머지는 유지한다. 429는 한도가 찬 상태라 재시도로 성공하지 않고 오류도 호출 한도를 소모한다(NFR-04). 행동 기록은 자체 데이터이므로 네이버 상태와 분리한다. 한도 초과 안내 문구는 MVP 화면을 만들 때 정한다. 카카오 이미지 검색으로 대체하는 안은 후순위로 두었다. ([D-03](./decisions.md)) |
| NFR-10 | 반응형 웹으로 만들어 휴대폰 화면 너비에서도 홈 갤러리, 검색, 지도와 가게 카드를 쓸 수 있게 한다. 화면 너비에 따라 갤러리의 열 수가 바뀌고, 지도 위 버튼과 카드는 손가락으로 누를 수 있는 크기로 한다. 모바일에서 디저트 구역을 어떻게 배치할지는 MVP 화면을 만들 때 정한다. | 디저트 사진을 보고 가게를 찾아가는 서비스라 이동 중 휴대폰에서 열 가능성이 높다. 별도 모바일 앱이나 모바일 전용 페이지를 만들지 않고 하나의 웹페이지가 화면 너비에 맞춰 바뀌게 하는 것이 GT의 결정이다. 위치 권한은 모바일에서 가장 자연스럽게 쓰이므로 NFR-01과 함께 고려한다. |

## 5. 데이터 요구사항

> 랭킹 기준과 데이터 출처를 정한다. 엔터티와 속성, 이후 ERD의 출발점이 된다.

- 랭킹: 보여주지 않는다. 홈에는 작성자가 고른 유행 디저트 몇 개를 두고, 사용자가 이름으로 검색한다. ([D-07](./decisions.md))
- 데이터 출처(초기): 이미지는 네이버 이미지 검색 API를 사용자 검색 시점에 호출해 가공 없이 보여준다. 네이버 결과는 저장하지 않는다. 디저트 후보 이름은 작성자가 고른 목록과 사용자의 검색어다. 가게는 네이버 지역 검색 API로 요청 시점에 조회해 지도에 표시하며 저장하지 않는다. ([D-03](./decisions.md), [D-06](./decisions.md), [D-07](./decisions.md))
- 사용자 행동 기록: 사용자가 검색한 디저트 이름만 처음부터 기록한다. 이후 유행 지표의 원천 데이터가 된다. 기록 항목은 익명 기기 ID, 검색한 디저트 이름, 시각이며 IP·좌표·이메일 등은 넣지 않는다. 기기 ID는 브라우저가 만들어 브라우저에 저장한다. 보관 기간은 미정이다. ([D-02](./decisions.md), [D-05](./decisions.md))

### 5.1 디저트 테이블 (`dessert`)

홈에 노출할 디저트 목록이다. 작성자가 직접 넣고(FR-01), 네이버 결과는 담지 않는다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT, 자동 증가, PK | 행을 구분하는 번호 |
| `keyword` | VARCHAR(100), NOT NULL, UNIQUE | 화면에 보이면서 네이버에도 보내는 이름 (예: 두쫀쿠) |
| `visible` | BOOLEAN, NOT NULL, 기본 true | 홈에 노출할지 여부 |
| `created_at` | TIMESTAMPTZ, NOT NULL, 기본 now() | 등록 시각 |

- 홈은 `visible = true`인 행에서 무작위로 최대 3개를 뽑는다. 행이 수십 개 수준이라 `ORDER BY random() LIMIT 3` 같은 단순한 쿼리로 충분하다.
- 행동 기록(FR-08)은 이 테이블을 외래 키로 참조하지 않고 검색한 이름을 문자열로 저장한다. 사용자는 목록에 없는 디저트도 검색할 수 있기 때문이다.
- 시작용 디저트의 개수와 품목은 작성자(GT)가 정한다. 미정이다.
- 설계 근거는 [D-08](./decisions.md)에 있다.

### 5.2 행동 기록 테이블 (`search_log`)

사용자가 검색한 디저트 이름을 기록한다(FR-08). 이 테이블에는 NFR-02에서 정한 항목만 넣는다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT, 자동 증가, PK | 행을 구분하는 번호 |
| `device_id` | UUID, NOT NULL | 브라우저가 만든 익명 기기 ID |
| `keyword` | VARCHAR(100), NOT NULL | 사용자가 검색한 디저트 이름 |
| `time` | TIMESTAMPTZ, NOT NULL, 기본 now() | 검색 시각 (마지막 컬럼) |

- `keyword`는 `dessert` 테이블을 외래 키로 참조하지 않는다. 사용자는 목록에 없는 디저트도 검색하기 때문이다.
- `keyword`에 `UNIQUE`를 걸지 않는다. 같은 사람이 같은 디저트를 반복 검색하는 것도 신호다.
- 인덱스는 처음에 두지 않는다. 유행 집계가 MVP 범위 밖이라(D-02), 집계가 필요해질 때 `keyword`와 `time`에 추가한다.
- 원본 기록의 보관 기간은 길게 가져가지 않는다. 일정 시점마다 키워드별 검색 횟수를 통계 테이블에 모으는 방안을 나중에 설계한다. 기간과 통계 테이블 구조는 미정이다.
- 설계 근거는 [D-09](./decisions.md)에 있다.
