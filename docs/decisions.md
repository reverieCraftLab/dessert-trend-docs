# 결정 기록

실제 사이트를 만드는 결정만 기록합니다. 항목마다 "정한 것 / 이유 / 다른 선택지"를 남겨서, 나중에 왜 그렇게 했는지 설명할 수 있게 하는 것이 목적입니다.

## D-01. 주 타깃은 일반 유저, 소상공인은 서브로 한다 (2026-10-17)

- **정한 것**: 주 타깃을 일반 유저로, 소상공인을 서브 타깃으로 한다.
- **이유**: 이 프로젝트의 핵심이 핀터레스트 스타일로 디저트를 둘러보고 가게를 찾는 경험이라서, 일반 유저 중심이 프로젝트에 맞다고 판단했다.
- **다른 선택지**: 소상공인을 주 타깃으로 하는 유행 시점 판단 서비스. 처음에 고려했던 방향이다.

## D-02. 유행 지표 화면은 MVP에서 제외하고, 행동 기록은 처음부터 한다 (2026-10-17)

- **정한 것**: 소상공인용 유행 지표 화면은 나중에 추가한다. 대신 사용자의 특정 행동은 초기부터 기록한다. 소상공인용 확장 기능으로, 쇼핑 인사이트를 이용해 재료 키워드의 관심 변화를 보는 기능도 나중에 추가한다.
- **이유**: 사용자가 모이기 전에는 행동 데이터로 만든 지표가 유효하지 않아서 화면은 미룬다. 반면 기록은 미룰 수 없다. 지표를 나중에 붙이려면 그때까지 쌓인 데이터가 필요하고, 네이버가 API를 앞으로도 계속 제공한다는 보장이 없어서 외부 데이터에만 의존하면 위험하기 때문이다.
- **다른 선택지**: 처음부터 지표 화면을 만들기. Data Lab 같은 외부 지표를 중심으로 만들기(네이버 의존도가 커져서 택하지 않았다).
- **남은 과제**: 어떤 행동을 기록할지 정한다. Data Lab 지표를 보조로 쓸지 정한다.

## D-03. 초기 데이터는 외부 API(네이버)로 가져온다 (2026-10-17)

- **정한 것**: 초기 데이터는 외부 API로 가져오고, 네이버 API를 최종 후보로 한다. 대상은 NAVER 검색(이미지, 블로그, 지역, 뉴스, 카페)과 Data Lab(검색어트렌드, 쇼핑인사이트)이다.
- **이유**: 무료 요청 횟수가 많다고 판단했고, 한국에서는 맛집과 위치를 찾을 때 네이버 지도를, 후기를 볼 때 네이버 블로그를 많이 쓰므로 네이버가 가장 효율이 좋다고 보았다.
- **다른 선택지**: 카카오 등 다른 API. 비교는 아직 하지 않았다.
- **확인한 것**: 네이버 API 허브 콘솔 화면 기준 NAVER 검색은 일 25,000회·월 775,000회, Data Lab은 API별 월 50,000회로 표시된다.
- **확인한 것(제공 기능)**: 네이버 API 허브 상품 소개 페이지 기준으로, 이미지 검색은 썸네일 구성 등에 쓰는 이미지 검색 결과를, 지역 검색은 네이버 지역 서비스에 등록된 업체·기관 검색 결과를 제공한다. 검색어 트렌드와 쇼핑 인사이트는 조회 기간 내 최고 시점을 100으로 두고 나머지를 환산한 상대 지표로 제공한다. 이 페이지에는 이미지 이용 약관이 나와 있지 않다.
- **확인한 것(공식 약관 원문)**: NAVER API 서비스 이용약관(NAVER API HUB, 시행 2026.09.20) 기준이다.
  - 검색 API는 네이버 검색결과를 보여주는 목적으로만 쓸 수 있다. 네이버 검색결과임을 BI 가이드에 따라 표시하고, 원본 출처와 원본으로 가는 링크를 제공해야 한다. (특약 1.1, 1.2)
  - 결과는 독립적으로, 가공 없이 노출해야 한다. 결과의 앞·뒤·중간에 다른 내용을 넣거나 순위·내용을 바꿀 수 없다. (특약 1.2)
  - 데이터(가공·파생물 포함)의 복사·저장·캐싱, 제3자 제공·판매, AI 입력·학습, 결과가 표시되는 페이지의 광고와 수익 창출이 금지된다. (특약 1.3)
  - 예외로 서비스 연속성에 필요한 임시 보관만 허용된다. 기기는 24시간 또는 새 질의 시까지 중 짧은 기간, 서버는 이력 조회 목적에 한해 최대 21일이다. (특약 1.4)
  - 일반 조건에서도 결과 데이터의 무단 저장(캐시 포함)·가공을 금지하고, 지역정보를 별도 DB로 관리하는 것을 예로 든다. API 결과 화면과 함께 광고를 노출하는 것도 금지한다. (7.3의 ③, ④)
  - 네이버는 서비스를 변경할 수 있고, 무료 API 결과의 지속성을 보증하지 않는다. (9.1, 10.1)
  - 위 특약은 "네이버 검색 API 서비스"에만 명시되어 있다. Data Lab은 특약이 없어 일반 조건이 적용되는데, 일반 조건의 "API 제공 취지에 맞지 않는 저장" 금지가 Data Lab 시계열 저장에 어떻게 적용되는지는 약관만으로 알 수 없다.
- **확인한 것(API 문서)**: Data Lab의 검색어 트렌드와 쇼핑 인사이트는 입력한 키워드나 분야의 추이(상대값)만 주고, 인기 검색어나 순위 목록을 주는 기능은 문서에 없다. 검색어 트렌드는 한 요청에 주제어 최대 5쌍까지 넣을 수 있다. 따라서 "네이버에서 많이 검색된 디저트 이름을 가져온다"는 방식은 이 API로는 불가능하고, 디저트 후보 이름은 다른 방법으로 얻어야 한다.
- **확인한 것(가게 검색 API)**: 네이버 지역 검색은 요청당 최대 5개이고 좌표·반경 파라미터가 없다. 네이버 클라우드 지도(Maps) 서비스에는 지도 표시, 주소 검색(Geocoding), 경로 API는 있지만 장소(가게) 검색 API는 문서에 없다. 따라서 "내 위치 주변"이나 "지도 영역 안" 가게 검색은 네이버 API만으로는 어렵다. 대신 네이버 지도 앱 URL Scheme(`nmap://search?query=`)은 앱의 통합 검색을 열어 준다. 네이버 지도 앱이 설치된 기기에서만 동작하고, 이 검색 액션에는 위치 파라미터가 없다. 카카오 로컬 API는 좌표·반경과 지도 영역 검색을 지원하지만 약관은 아직 확인하지 않았다.
- **확인한 것(카카오, 공식 FAQ·약관)**: 카카오맵 API FAQ는 "로컬 API 등을 호출하여 응답받은 결과 데이터를 별도로 저장하여 사용하는 것은 허용하지 않습니다"라고 한다. 네이버와 같이 실시간 호출만 가능하다. 운영정책(시행 2026.04.20) 제5조 제20호도 사용자 환경 개선 목적 외의 캐시를 금지한다. 상업적 서비스는 약관과 운영정책을 지키면 별도로 막지 않지만, API 재판매와 API 기능에 대한 별도 과금은 허용되지 않는다. 광고에 대한 구체적 언급은 없다. 무료 쿼터는 장소 검색(키워드·카테고리) 일 100,000건, 지도 Web SDK 일 300,000건, 전체 월 3,000,000건이고 처음 활성화한 앱에만 제공된다. 초과분은 장소 검색 2원/건이다(쿼터 문서 기준, 변경될 수 있음). 사용자 위치 정보에 특화된 조항은 없었다.
- **확인한 것(카카오, 개발자 포럼 답변)**: "Map"이라는 닉네임의 답변(카카오 직원 표시는 없음)에 따르면 임시 저장도 허용되지 않는다. 장소 ID만 기록하고 표시 정보는 실시간 호출하는 방식은 운영정책상 허용 가능한 방향이라고 했지만, ID로 단건 조회하는 API가 없어 자체 설계가 필요하다고 한다. 타사 지도 위에 표시하는 것을 제한하지 않는다는 답변도 있었다. 모두 공식 확인으로 보기는 어렵다.
- **확인하지 못한 것(카카오)**: 지도 SDK의 장소 검색 사용법(문서 목차에서 이름만 확인), 메뉴 이름 검색 정확도.
- **확인하지 못한 것**: 앞서 2차 자료에 있던 "검색 API 신규 신청 중단, 2027년 6월 30일까지 사용 가능"은 이 약관 원문에 없어서 문서에서 뺐다.
- **이 결정에 미치는 영향**: 검색 API 결과를 수집해 DB에 쌓고 그것으로 갤러리나 지표를 만드는 방식은 약관과 맞지 않는다. 처음 결정의 "네이버 API로 초기 데이터를 가져온다"는 저장 방식과 용도를 다시 정해야 한다. 이 약관 내용은 D-02의 "네이버에만 의존하지 않고 행동 데이터를 처음부터 기록한다"는 판단을 뒷받침한다.
- **남은 과제**: 갤러리의 이미지와 가게 정보의 출처를 다시 정한다. Data Lab 결과의 저장 가능 여부는 약관 문의(NAVER API HUB 문의하기)로 확인한다. 각 API를 어떤 용도로 쓸지 정한다.

## D-04. 처음에는 로그인 없이 동작하고, 저장 기록은 기기에 둔다 (2026-10-20)

- **정한 것**: 초기에는 회원가입·로그인 없이 사용한다. 저장·히스토리는 사용자의 기기에 보관하고, 기기를 바꾸거나 데이터를 삭제하면 사라진다는 점을 서비스에서 안내한다. 기기가 바뀌어도 기록이 이어지게 하는 시점에 회원가입·로그인을 추가한다.
- **이유**: 가입 절차 없이 바로 써 볼 수 있게 한다. (대화에서 Claude가 장단점으로 제시한 내용 기준이며, GT의 이유와 다르면 고친다.)
- **다른 선택지**: 처음부터 회원가입·로그인. 기기를 바꿔도 이어지고 사용자 단위로 행동 기록을 쌓기 쉽지만, 가입이라는 문턱이 생긴다.
- **감수하는 점**: 기기를 바꾸거나 데이터를 지우면 저장 기록이 사라진다. 서버 행동 기록(D-02)도 사용자 단위로 묶기 어렵다.
- **남은 과제**: 서버 행동 기록은 익명 기기 ID로 묶기로 했다([D-05](#d-05-행동-기록은-익명-기기-id로-묶는다-2026-10-20)). 기기에 저장하는 데이터가 네이버 API 결과를 포함하면 약관의 기기 보관 제한(24시간)에 걸릴 수 있으므로, 자체 디저트 식별자만 저장하는지 확인한다.

## D-05. 행동 기록은 익명 기기 ID로 묶는다 (2026-10-20)

- **정한 것**: 서버에 쌓는 행동 기록에 익명 기기 ID를 함께 기록한다. 익명 기기 ID는 로그인과 무관하게 기기(또는 앱 설치)마다 만든 임의의 ID다.
- **이유**: 나중에 모바일 앱으로도 만들 계획이다. (GT) 추가 근거는 Claude가 제시한 것이다. 앱에서도 설치 단위의 ID로 같은 방식을 쓸 수 있고, 나중에 로그인을 추가하면 이 ID와 계정을 연결해서 그동안 쌓은 기록을 이어 붙일 수 있다. 같은 기기의 중복 클릭을 걸러 지표가 부풀려지는 것도 줄인다.
- **다른 선택지**: ID 없이 디저트, 행동 종류, 시각만 기록. 개인 식별 부담은 작지만 중복 클릭을 걸러내기 어렵고, 로그인을 추가할 때 기록을 이어 붙일 수 없다.
- **감수하는 점**: 이 ID와 행동 기록이 개인정보 처리 대상이 될 수 있어 안내와 보관 기준이 필요하다. 웹 브라우저와 앱은 서로 다른 ID를 가지므로 로그인 전에는 같은 사람이 둘로 보인다. 기기 데이터를 삭제하면 ID도 새로 만들어져 새 기기로 취급된다(D-04와 같은 전제).
- **남은 과제**: ID를 클라이언트가 만들지 서버가 발급할지, 어디에 저장하고 얼마나 보관할지 정한다. 개인정보 처리방침에 넣을 내용을 정리한다(법률 자문은 아니다). 앱을 만들 때는 광고 식별자 대신 앱이 자체 생성하는 ID를 쓰는 것이 일반적이라고 알려져 있으므로, 그때 각 스토어 정책을 확인한다.

## D-06. 사용자 위치는 브라우저에서만 쓰고, 지도 검색은 버튼으로 한다 (2026-10-20)

- **정한 것**: (1) 사용자의 위치는 브라우저에서만 사용하고 서버로 보내거나 저장하지 않는다. 행동 기록(D-05)에도 좌표를 넣지 않는다. (2) 지도 화면은 위치 권한이 없으면 지정한 기본 위치에서 시작하고, 사용자가 지도를 옮긴 뒤 "이 위치에서 검색" 버튼을 눌렀을 때만 그 위치로 검색한다.
- **이유**: (1) 위치는 민감한 정보라 서버에 두면 동의·안내·신고 같은 부담이 커질 수 있다. 서버에 두지 않으면 이 부담을 줄일 수 있다. 법적 판단은 확인이 필요하다(법률 자문은 아니다). (2) 이동할 때마다 검색하면 호출이 낭비되고 결과가 계속 바뀌어 혼란스럽다. 버튼으로 하면 호출 시점이 사용자의 의도와 일치한다. (2)의 이유는 Claude가 제시한 것이다.
- **다른 선택지**: 위치를 서버로 보내 처리하기(서버에서 검색과 기록이 가능하지만 위 부담이 생긴다). 지도를 옮길 때마다 자동으로 검색하기.
- **남은 과제**: 이미지를 누르면 지도에서 주변 가게를 검색하는 흐름 자체는, 가게 검색의 데이터 출처와 메뉴 이름 검색 정확도를 확인한 뒤 확정한다.
