# 결정 기록

실제 사이트를 만드는 결정만 기록합니다. 항목마다 "정한 것 / 이유 / 다른 선택지"를 남겨서, 나중에 왜 그렇게 했는지 설명할 수 있게 하는 것이 목적입니다.

## D-01. 주 타깃은 일반 유저, 소상공인은 서브로 한다 (2026-10-17)

- **정한 것**: 주 타깃을 일반 유저로, 소상공인을 서브 타깃으로 한다.
- **이유**: 이 프로젝트의 핵심이 핀터레스트 스타일로 디저트를 둘러보고 가게를 찾는 경험이라서, 일반 유저 중심이 프로젝트에 맞다고 판단했다.
- **다른 선택지**: 소상공인을 주 타깃으로 하는 유행 시점 판단 서비스. 처음에 고려했던 방향이다.

## D-02. 유행 지표 화면은 MVP에서 제외하고, 행동 기록은 처음부터 한다 (2026-10-17)

- **정한 것**: 소상공인용 유행 지표 화면은 나중에 추가한다. 대신 사용자의 특정 행동은 초기부터 기록한다. 소상공인용 확장 기능으로, 쇼핑 인사이트를 이용해 재료 키워드의 관심 변화를 보는 기능도 나중에 추가한다.
- **이유**: 사용자가 모이기 전에는 행동 데이터로 만든 지표가 유효하지 않아서 화면은 미룬다. 반면 기록은 미룰 수 없다. 지표를 나중에 붙이려면 그때까지 쌓인 데이터가 필요하고, 네이버가 API를 앞으로도 계속 제공한다는 보장이 없어서 외부 데이터에만 의존하면 위험하기 때문이다.
- **다른 선택지**: 처음부터 지표 화면을 만들기. Data Lab 같은 외부 지표를 중심으로 만들기(네이버 의존도가 커져서 택하지 않았다).
- **남은 과제**: 어떤 행동을 기록할지 정한다. Data Lab 지표를 보조로 쓸지 정한다.

## D-03. 초기 데이터는 외부 API(네이버)로 가져온다 (2026-10-17)

- **정한 것**: 초기 데이터는 외부 API로 가져오고, 네이버 API를 최종 후보로 한다. 대상은 NAVER 검색(이미지, 블로그, 지역, 뉴스, 카페)과 Data Lab(검색어트렌드, 쇼핑인사이트)이다.
- **이유**: 무료 요청 횟수가 많다고 판단했고, 한국에서는 맛집과 위치를 찾을 때 네이버 지도를, 후기를 볼 때 네이버 블로그를 많이 쓰므로 네이버가 가장 효율이 좋다고 보았다.
- **다른 선택지**: 카카오 등 다른 API. 비교는 아직 하지 않았다.
- **확인한 것**: 네이버 API 허브 콘솔 화면 기준 NAVER 검색은 일 25,000회·월 775,000회, Data Lab은 API별 월 50,000회로 표시된다.
- **확인한 것(제공 기능)**: 네이버 API 허브 상품 소개 페이지 기준으로, 이미지 검색은 썸네일 구성 등에 쓰는 이미지 검색 결과를, 지역 검색은 네이버 지역 서비스에 등록된 업체·기관 검색 결과를 제공한다. 검색어 트렌드와 쇼핑 인사이트는 조회 기간 내 최고 시점을 100으로 두고 나머지를 환산한 상대 지표로 제공한다. 이 페이지에는 이미지 이용 약관이 나와 있지 않다.
- **확인한 것(공식 약관 원문)**: NAVER API 서비스 이용약관(NAVER API HUB, 시행 2026.09.20) 기준이다.
  - 검색 API는 네이버 검색결과를 보여주는 목적으로만 쓸 수 있다. 네이버 검색결과임을 BI 가이드에 따라 표시하고, 원본 출처와 원본으로 가는 링크를 제공해야 한다. (특약 1.1, 1.2)
  - 결과는 독립적으로, 가공 없이 노출해야 한다. 결과의 앞·뒤·중간에 다른 내용을 넣거나 순위·내용을 바꿀 수 없다. (특약 1.2)
  - 데이터(가공·파생물 포함)의 복사·저장·캐싱, 제3자 제공·판매, AI 입력·학습, 결과가 표시되는 페이지의 광고와 수익 창출이 금지된다. (특약 1.3)
  - 예외로 서비스 연속성에 필요한 임시 보관만 허용된다. 기기는 24시간 또는 새 질의 시까지 중 짧은 기간, 서버는 이력 조회 목적에 한해 최대 21일이다. (특약 1.4)
  - 일반 조건에서도 결과 데이터의 무단 저장(캐시 포함)·가공을 금지하고, 지역정보를 별도 DB로 관리하는 것을 예로 든다. API 결과 화면과 함께 광고를 노출하는 것도 금지한다. (7.3의 ③, ④)
  - 네이버는 서비스를 변경할 수 있고, 무료 API 결과의 지속성을 보증하지 않는다. (9.1, 10.1)
  - 위 특약은 "네이버 검색 API 서비스"에만 명시되어 있다. Data Lab은 특약이 없어 일반 조건이 적용되는데, 일반 조건의 "API 제공 취지에 맞지 않는 저장" 금지가 Data Lab 시계열 저장에 어떻게 적용되는지는 약관만으로 알 수 없다.
- **확인한 것(API 문서)**: Data Lab의 검색어 트렌드와 쇼핑 인사이트는 입력한 키워드나 분야의 추이(상대값)만 주고, 인기 검색어나 순위 목록을 주는 기능은 문서에 없다. 검색어 트렌드는 한 요청에 주제어 최대 5쌍까지 넣을 수 있다. 따라서 "네이버에서 많이 검색된 디저트 이름을 가져온다"는 방식은 이 API로는 불가능하고, 디저트 후보 이름은 다른 방법으로 얻어야 한다.
- **확인한 것(가게 검색 API)**: 네이버 지역 검색은 요청당 최대 5개이고 좌표·반경 파라미터가 없다. 네이버 클라우드 지도(Maps) 서비스에는 지도 표시, 주소 검색(Geocoding), 경로 API는 있지만 장소(가게) 검색 API는 문서에 없다. 따라서 "내 위치 주변"이나 "지도 영역 안" 가게 검색은 네이버 API만으로는 어렵다. 대신 네이버 지도 앱 URL Scheme(`nmap://search?query=`)은 앱의 통합 검색을 열어 준다. 네이버 지도 앱이 설치된 기기에서만 동작하고, 이 검색 액션에는 위치 파라미터가 없다. 카카오 로컬 API는 좌표·반경과 지도 영역 검색을 지원하지만 약관은 아직 확인하지 않았다.
- **확인한 것(카카오, 공식 FAQ·약관)**: 카카오맵 API FAQ는 "로컬 API 등을 호출하여 응답받은 결과 데이터를 별도로 저장하여 사용하는 것은 허용하지 않습니다"라고 한다. 네이버와 같이 실시간 호출만 가능하다. 운영정책(시행 2026.04.20) 제5조 제20호도 사용자 환경 개선 목적 외의 캐시를 금지한다. 상업적 서비스는 약관과 운영정책을 지키면 별도로 막지 않지만, API 재판매와 API 기능에 대한 별도 과금은 허용되지 않는다. 광고에 대한 구체적 언급은 없다. 무료 쿼터는 장소 검색(키워드·카테고리) 일 100,000건, 지도 Web SDK 일 300,000건, 전체 월 3,000,000건이고 처음 활성화한 앱에만 제공된다. 초과분은 장소 검색 2원/건이다(쿼터 문서 기준, 변경될 수 있음). 사용자 위치 정보에 특화된 조항은 없었다.
- **확인한 것(카카오, 개발자 포럼 답변)**: "Map"이라는 닉네임의 답변(카카오 직원 표시는 없음)에 따르면 임시 저장도 허용되지 않는다. 장소 ID만 기록하고 표시 정보는 실시간 호출하는 방식은 운영정책상 허용 가능한 방향이라고 했지만, ID로 단건 조회하는 API가 없어 자체 설계가 필요하다고 한다. 타사 지도 위에 표시하는 것을 제한하지 않는다는 답변도 있었다. 모두 공식 확인으로 보기는 어렵다.
- **확인하지 못한 것(카카오)**: 지도 SDK의 장소 검색 사용법(문서 목차에서 이름만 확인), 메뉴 이름 검색 정확도.
- **확인하지 못한 것**: 앞서 2차 자료에 있던 "검색 API 신규 신청 중단, 2027년 6월 30일까지 사용 가능"은 이 약관 원문에 없어서 문서에서 뺐다.
- **확인한 것(네이버 문의 답변, 2026-10-20)**: 네이버 클라우드 플랫폼에 4가지를 문의했고 답변을 받았다.
  - 문의 1(결과를 계산만 하고 집계 수치만 보관): 계산한 뒤 보관하므로 가공·파생물의 복사·저장·캐싱에 해당한다는 답변이다. 허용되는 형태는 안내받지 못했다.
  - 문의 2(Data Lab ratio 저장·표시)와 문의 3(항목 URL만 저장하고 표시 때마다 재호출): 답변은 두 문의를 묶어서, 약관 7.3에 따라 DB나 AI에 데이터를 저장하는 것은 금지라고 했다. 문의 2의 (b) 저장 기간과 (c) 출처 표기는 답변에 없다. URL만 저장하는 방식을 별도로 짚은 답변도 없어서, 문의 3은 "허용된다는 답을 받지 못했고 7.3에 따라 금지로 본다"가 정확하다.
  - 문의 4(이미지 그리드 표시): 가공 없이 노출하는 요건에 맞는다는 답변이다. 문의에서 제시한 조건(API 순서 유지, 결과 사이에 다른 콘텐츠 없음, 출처·원본 링크·BI 표기)을 전제로 한 답이다.
  - 답변이 특히 확인하라고 안내한 조항: 7.2③(사용자에게 API 이용 대가를 받는 행위 금지), 7.3③(무단 복제·저장·가공·배포·제3자 제공 금지), 7.3④(결과 화면과 광고 노출 금지), 7.3⑤(다수의 클라이언트 ID 사용 금지), 7.3⑫(자동화 프로그램 접속 및 주기적·지속적 접속으로 인한 과부하 금지), 8.1·8.2(결과 데이터의 권리 귀속과 사용권 범위). 이 중 7.2③, 7.3⑤, 7.3⑫는 이전에 정리하지 않은 조항이다. 약관 원문으로 확인이 필요하다.
- **확인한 것(약관 원문, 답변이 안내한 조항)**: 약관 원문 기준이고, "서비스에 주는 영향"은 Claude의 해석이라 네이버 확인을 받은 것이 아니다.
  - 7.2③: 이용자는 애플리케이션의 사용자들로부터 API 서비스 이용에 대한 대가(금전, 정보 제공 등 일체의 유·무형의 대가)를 제공받아서는 안 된다. 영향: API 결과를 쓰는 기능에 요금을 받을 수 없다. 소상공인용 유료 지표를 만든다면 네이버 데이터가 아닌 우리 행동 기록으로만 만들어야 한다. "정보 제공"까지 대가로 보는 문구라서, API 기능을 쓰는 조건으로 사용자에게 개인정보 입력을 요구하는 설계(예: 가입 필수)는 문의로 확인하는 것이 안전하다. 현재 MVP는 무료이고 로그인이 없다(D-04).
  - 7.3⑤: API 허용량을 늘리거나 데이터를 추출·저장할 목적으로, 동일한 애플리케이션이나 동일한 목적의 애플리케이션에서 다수의 클라이언트 ID를 사용해 호출하는 행위를 금지한다. 영향: 한도 때문에 키를 여러 개 돌려 쓰는 설계는 안 된다. 개발용과 운영용 앱을 따로 두는 것은 문구상 "허용량을 늘리거나 추출 저장하는 목적"이 아니라서 금지 대상으로 보이지 않지만, 확정은 아니다.
  - 7.3⑫: 서버에 자동화 프로그램으로 접속하거나, 접근권한을 넘어서거나, 주기적·지속적 접속으로 과부하를 발생시키는 방식의 접근을 금지한다. 영향: "주기적 접속" 자체가 아니라 "과부하를 발생시키는 방식"이 금지의 요건으로 읽힌다. 다만 저장이 금지되어 있어서 정기 수집 배치의 쓸모가 거의 없고, 호출은 사용자 요청 때에 맞춰 하는 방식이 약관과 가장 잘 맞는다.
  - 8.1·8.2: 결과 데이터의 저작권은 네이버 또는 원저작자 등 제3자에게 있고, 이용 승낙은 제한된 사용권일 뿐 결과 데이터에 대한 권리 취득을 뜻하지 않는다. 영향: 갤러리 이미지는 우리 것이 아니라 원 저작자의 것을 가공 없이 빌려 보여주는 것이다. 이미지로 가게 광고를 하거나 우리 콘텐츠로 재가공하는 용도에는 쓸 수 없다고 봐야 한다.
- **이 결정에 미치는 영향**: 검색 API 결과를 수집해 DB에 쌓고 그것으로 갤러리나 지표를 만드는 방식은 약관과 맞지 않는다. 처음 결정의 "네이버 API로 초기 데이터를 가져온다"는 저장 방식과 용도를 다시 정해야 한다. 이 약관 내용은 D-02의 "네이버에만 의존하지 않고 행동 데이터를 처음부터 기록한다"는 판단을 뒷받침한다.
- **남은 과제**: 문의 답변으로 네이버 결과의 집계·저장은 쓸 수 없는 것으로 정리되었다. 남은 것은 (1) 갤러리의 이미지와 디저트 후보 이름의 출처를 정하는 것, (2) 사용자의 저장 기능(SC-03)이 네이버 URL 대신 어떤 식별자를 저장할지 정하는 것, (3) Data Lab을 저장 없이 실시간 조회로만 쓸지 정하는 것, (4) 7.2③의 "정보 제공 등 유·무형의 대가"가 가입 요구에 해당하는지 필요하면 문의하는 것이다. 7.3⑤·⑫·8은 원문으로 정리했다. (5) 네이버 한도 소진이나 장애 때 카카오 이미지 검색으로 대체하는 안은 2026-10-21 후순위로 미뤘다. 사용자가 늘어난 뒤에 판단한다. 그때 확인할 것은 카카오 이미지 검색의 약관(저장·출처 표기), 결과 품질, 그리고 네이버 결과와 섞지 않고 영역 전체를 대체하는 방식이 네이버 특약 1.3에 어긋나지 않는지다.

## D-04. 처음에는 로그인 없이 동작하고, 저장 기록은 기기에 둔다 (2026-10-20)

- **정한 것**: 초기에는 회원가입·로그인 없이 사용한다. 저장·히스토리는 사용자의 기기에 보관하고, 기기를 바꾸거나 데이터를 삭제하면 사라진다는 점을 서비스에서 안내한다. 기기가 바뀌어도 기록이 이어지게 하는 시점에 회원가입·로그인을 추가한다.
- **이유**: 가입 절차 없이 바로 써 볼 수 있게 한다. (대화에서 Claude가 장단점으로 제시한 내용 기준이며, GT의 이유와 다르면 고친다.)
- **다른 선택지**: 처음부터 회원가입·로그인. 기기를 바꿔도 이어지고 사용자 단위로 행동 기록을 쌓기 쉽지만, 가입이라는 문턱이 생긴다.
- **감수하는 점**: 기기를 바꾸거나 데이터를 지우면 저장 기록이 사라진다. 서버 행동 기록(D-02)도 사용자 단위로 묶기 어렵다.
- **남은 과제**: 서버 행동 기록은 익명 기기 ID로 묶기로 했다([D-05](#d-05-행동-기록은-익명-기기-id로-묶는다-2026-10-20)). 기기에 저장하는 데이터가 네이버 API 결과를 포함하면 약관의 기기 보관 제한(24시간)에 걸릴 수 있으므로, 자체 디저트 식별자만 저장하는지 확인한다.
- **갱신(2026-10-21)**: MVP에서는 디저트 저장 기능 자체를 미루기로 했다(FR-07). 위 설계는 저장 기능을 추가할 때 적용한다. 익명 기기 ID 기록(D-05)은 MVP에 남는다.

## D-05. 행동 기록은 익명 기기 ID로 묶는다 (2026-10-20)

- **정한 것**: 서버에 쌓는 행동 기록에 익명 기기 ID를 함께 기록한다. 익명 기기 ID는 로그인과 무관하게 기기(또는 앱 설치)마다 만든 임의의 ID다.
- **이유**: 나중에 모바일 앱으로도 만들 계획이다. (GT) 추가 근거는 Claude가 제시한 것이다. 앱에서도 설치 단위의 ID로 같은 방식을 쓸 수 있고, 나중에 로그인을 추가하면 이 ID와 계정을 연결해서 그동안 쌓은 기록을 이어 붙일 수 있다. 같은 기기의 중복 클릭을 걸러 지표가 부풀려지는 것도 줄인다.
- **다른 선택지**: ID 없이 디저트, 행동 종류, 시각만 기록. 개인 식별 부담은 작지만 중복 클릭을 걸러내기 어렵고, 로그인을 추가할 때 기록을 이어 붙일 수 없다.
- **감수하는 점**: 이 ID와 행동 기록이 개인정보 처리 대상이 될 수 있어 안내와 보관 기준이 필요하다. 웹 브라우저와 앱은 서로 다른 ID를 가지므로 로그인 전에는 같은 사람이 둘로 보인다. 기기 데이터를 삭제하면 ID도 새로 만들어져 새 기기로 취급된다(D-04와 같은 전제).
- **정한 것(기록 항목과 개인정보, 2026-10-21)**: (GT) 기록하는 행동은 사용자가 검색한 디저트 이름뿐이다. 기록 항목은 익명 기기 ID, 검색한 디저트 이름, 시각이다. 기기 ID는 브라우저가 만들어 브라우저에 저장하고, 사용자가 지울 수 있다. IP, 좌표, 이메일은 행동 기록에 넣지 않는다. 검색어는 길이를 제한하고 개인정보로 보이는 입력은 저장하지 않는 처리를 검토한다. 기록 내용과 지우는 방법은 서비스 안에서 안내한다. 나중에 로그인을 붙일 때는 기기 ID와 계정을 연결하기 전에 동의를 받는다. 보관 기간은 미정이다.
- **이유(개인정보)**: (Claude, 법률 자문 아님) 개인정보 보호법 제2조는 그 자체로는 개인을 알아볼 수 없어도 다른 정보와 쉽게 결합해 알아볼 수 있으면 개인정보에 포함한다고 한다. 익명 기기 ID는 단독으로는 개인을 알아보기 어렵지만, 나중에 로그인과 연결하면 기존 기록이 계정과 결합된다. 서버 로그의 IP와 한 곳에서 합칠 수 있어도 식별 가능성이 커진다. 검색어는 자유 입력이라 사용자가 개인정보를 직접 입력할 수 있다. 그래서 수집 항목을 줄이고 결합 전에 동의를 받는 쪽으로 정했다.
- **다른 선택지**: 행동을 더 많이 기록하기(이미지 클릭, 가게 보기 등. 지표가 풍부해지지만 개인정보 부담이 커져 처음에는 택하지 않음). 기기 ID를 서버가 발급하기.
- **남은 과제**: 행동 기록의 보관 기간을 정한다. 기록 안내문의 문구를 정한다. 개인정보 처리방침이 법적으로 필요한지 확인한다.

## D-06. 사용자 위치는 브라우저에서만 쓰고, 지도 검색은 버튼으로 한다 (2026-10-20)

- **정한 것**: (1) 사용자의 위치는 브라우저에서만 사용하고 서버로 보내거나 저장하지 않는다. 행동 기록(D-05)에도 좌표를 넣지 않는다. (2) 지도 화면은 위치 권한이 없으면 지정한 기본 위치에서 시작하고, 사용자가 지도를 옮긴 뒤 "이 위치에서 검색" 버튼을 눌렀을 때만 그 위치로 검색한다.
- **이유**: (1) 위치는 민감한 정보라 서버에 두면 동의·안내·신고 같은 부담이 커질 수 있다. 서버에 두지 않으면 이 부담을 줄일 수 있다. 법적 판단은 확인이 필요하다(법률 자문은 아니다). (2) 이동할 때마다 검색하면 호출이 낭비되고 결과가 계속 바뀌어 혼란스럽다. 버튼으로 하면 호출 시점이 사용자의 의도와 일치한다. (2)의 이유는 Claude가 제시한 것이다.
- **다른 선택지**: 위치를 서버로 보내 처리하기(서버에서 검색과 기록이 가능하지만 위 부담이 생긴다). 지도를 옮길 때마다 자동으로 검색하기.
- **확인한 것(가게 검색 API 직접 호출, 2026-10-20)**: "두쫀쿠, 버터떡, 카다이프, 탕후루, 크루아상" 5개 키워드를 강남역 기준으로 호출했다.
  - 네이버 지역검색(`강남역 {키워드}`): 응답에 가게 이름, 카테고리, 도로명 주소, 좌표(`mapx`, `mapy`, 1e7을 곱한 값)가 모두 있어서 지도 마커에 바로 쓸 수 있다. 카다이프는 0건, 탕후루는 3건이었다. "강남역"은 필터가 아니라 검색어일 뿐이라 크루아상에는 용산·송파 가게가 섞였다. 가게 이름에 `&amp;` 같은 HTML 코드가 들어 있어 표시할 때 변환이 필요하다.
  - 카카오 로컬(강남역 좌표, 반경 2km, size 15): 반경 필터가 실제로 동작하고(결과 전부 2km 이내, 거리 포함) 한 번에 15개까지 받았다. 두쫀쿠 15곳 중 이디야커피가 8곳이었고, 카다이프는 1건, 탕후루는 0건이었다.
  - 판매 여부 확인(Claude, 2026-10-21): 구글 검색 결과의 블로그·인스타·메뉴 페이지 문구로 "두쫀쿠" 결과 가게를 확인했다(네이버 지도 페이지는 도구가 접근할 수 없어 못 봄). 네이버 5곳 중 4곳(셀렉티드닉스, 힉스커피, 카페 논현로, 잇테이블)은 가게 자체의 근거가 있었고 1곳(잇워즈굿)은 근거를 못 찾았다. 카카오 15곳 중 가게 자체의 근거가 확인된 곳은 0곳이었다. 11곳(이디야 8, 요거트아이스크림의정석 2, 요거트월드 1)은 체인 본사 차원에서 출시한 기록만 있고 해당 매장의 판매는 확인하지 못했다. 나머지 4곳(하마커피, 카페드빈, 잇워즈굿, 라떼킹 교대점)은 근거를 찾지 못했다. 근거는 대부분 2026년 1~3월 글이라 현재 판매 중인지는 별개이고, 키워드 하나와 위치 하나만 본 결과다.
  - 해석(Claude의 것이며 확인되지 않음): 두쫀쿠 한 키워드로는 네이버 지역검색이 메뉴까지 어느 정도 반영하고 카카오 로컬은 카페 카테고리와 체인 위주로 나오는 것으로 보인다. 다른 키워드(버터떡, 카다이프 등)로는 확인하지 않았고, 신조어는 두 API 모두 0~1건이 나왔다. 유행이 지나면 판매가 끝난 가게가 결과에 남을 수 있다.
  - 네이버 지도 웹 검색 화면 확인(GT가 캡처, 2026-10-21): `map.naver.com/p/search/두쫀쿠` 주소로 강남역 근처 결과가 지도 마커와 왼쪽 목록으로 나온다. 목록은 5페이지 이상이고 카드마다 리뷰 문구(두쫀쿠 언급)와 평점·리뷰 수가 보인다. 지도에는 "현 지도에서 검색" 버튼이 있고 영업중·예약·쿠폰·포장주문 필터가 있다. 첫 결과는 "광고"로 표시된 유료 노출이었다. API 5곳 중 셀렉티드닉스, 힉스커피, 잇워즈굿, 잇테이블 4곳이 지도 마커로 확인되었고(카페 논현로는 캡처 범위에 없음), 이 밖에도 어반스콘, 페임커피, 만땅커피 등 API가 주지 않은 가게가 많다. 즉 지도 검색은 API보다 훨씬 많은 결과를 주고, API 5곳은 그 결과의 일부로 보인다. 이 화면은 웹 버전이며 모바일 앱과 `nmap://` 링크 동작은 아직 확인하지 않았다.
- **정한 것(가게 검색 방식, 2026-10-21)**: 우리 홈페이지 안에서 네이버 Maps(Dynamic Map)로 지도를 보여주고, 네이버 지역검색 결과를 마커와 카드로 표시한다. 결과는 걸러내거나 순서를 바꾸지 않고, 결과 가게가 모두 보이도록 지도 범위를 맞춘다. "이 위치에서 검색"은 지도 중심 좌표를 지역명으로 바꿔 질의어에 넣는다. 결과가 없으면 지역을 넓혀 다시 조회하고, 그 사실을 화면에 알린다.
- **이유(가게 검색)**: (GT) 사용자가 우리 홈페이지에서 바로 보는 것이 가장 좋다고 판단했다. (Claude 확인) 지역검색 응답에 좌표가 있어 마커를 바로 찍을 수 있고, 두쫀쿠에서는 네이버 5곳 중 4곳의 판매 근거를 확인했다. 카카오는 반경 검색이 되고 15개까지 주지만 같은 키워드에서 체인 위주로 나와 선택하지 않았다. 네이버 지도(웹·앱)로 연결하는 안은 결과가 더 많고 리뷰 근거가 보이지만 우리 화면을 쓰지 못해 택하지 않았다.
- **약관 문의를 하지 않은 것(GT 판단)**: 마커 표시는 Maps의 기능을 쓰는 것이고, 지도 밖 결과를 숨기지 않으면 가공 문제가 생기지 않는다고 보았다. 공식 확인을 받은 것은 아니다.
- **범위 확장 재조회 테스트(2026-10-21)**: "강남역 카다이프", "강남구 카다이프"는 0건이었고 "서울 카다이프"는 5건이었다. 5건은 수입식품점 2곳, 기업, 햄버거집, 카페로 디저트 판매점과 거리가 있었다. "서울 탕후루"는 인천 부평점이 섞였다. 정확도가 낮은 것은 감수하기로 했다.
- **감수하는 점**: 한 번에 5곳까지만 나온다. 신조어와 재료성 키워드는 0건이거나 부정확하다. 유행이 끝난 뒤에도 판매를 중단한 가게가 결과에 남을 수 있다.
- **남은 과제**: 범위를 넓혀 재조회하는 정책은 [D-11](#d-11-범위-확장은-동역--구--시-순서로-자동으로-하고-알리지-않는다-2026-10-21)에서 정했다. 서버 공유 캐시와 한도 증량은 약관 문의 여부를 정한다(문의 문안은 작성했으나 발송하지 않음). 지도 중심 좌표를 지역명으로 바꾸는 방식(Reverse Geocoding)을 정한다. 서버 REST API로 호출하면 좌표가 서버를 거쳐 NFR-01(위치를 서버로 보내지 않음)에 어긋나므로, 브라우저에서 처리할 수 있는지(지도 JS의 geocoder 서브모듈 등, 미확인)를 확인해야 한다. 2026-10-21 MVP 화면을 만든 뒤 판단하기로 했다(화면이 있어야 실제 필요한 형태를 알 수 있고, 지금 정해도 되돌릴 수 있는 결정이라 늦춰도 비용이 작다).

## D-07. 실시간 자동 수집은 접고, 고른 유행 디저트와 사용자 검색으로 간다 (2026-10-20)

- **정한 것**: 홈에는 작성자가 고른 요즘 유행하는 디저트 몇 개를 두고, 랭킹은 보여주지 않는다. 사용자가 디저트 이름을 검색하면 네이버 이미지 검색 API를 그 시점에 호출해 결과를 가공 없이 보여준다. 실시간 유행은 이후 사용자의 검색어를 우리 DB에 쌓아서 만든다.
- **이유**: (GT) 유행하는 디저트를 실시간으로 수집하는 방법이 어렵다고 판단했고, 사용자가 디저트를 검색하다 보면 유행 정보가 자연스럽게 쌓일 것이라고 보았다. (Claude 확인) 공식 API 중 새 디저트 이름을 찾아주는 것이 없고(Data Lab은 입력한 키워드의 추이만 제공), 네이버 결과는 저장·집계·AI 입력이 금지다. 반면 이 방향은 문의 답변에서 허용된 "가공 없는 실시간 노출"만 쓰고, 사용자의 검색어는 네이버 데이터가 아니라 우리 데이터라서 저장해도 약관과 충돌하지 않는다.
- **이전 입장에서 바뀐 점**: "디저트 후보를 내가 직접 관리하는 것은 생각한 홈페이지가 아니다"에서, 자동 수집의 길이 막혀 초기 목록은 직접 고르는 것으로 바꾸었다. 목록은 시작용이고, 장기적으로는 사용자 검색어가 대신한다는 것이 GT의 방향이다.
- **다른 선택지**: 네이버에 데이터 제휴를 문의하기, 구글 트렌드 API(알파)나 유료 서드파티 데이터 쓰기, 사용자 제보 받기. 지금은 택하지 않았다. 사용자가 모인 뒤 다시 검토할 수 있다.
- **이 결정으로 풀리는 문제**: 디저트 후보 이름의 출처(고른 목록과 사용자 검색어), 사용자의 저장 기능(네이버 URL 대신 디저트 이름을 저장하고 다시 볼 때 검색을 다시 호출. [D-04](#d-04-처음에는-로그인-없이-동작하고-저장-기록은-기기에-둔다-2026-10-20)의 기기 저장과도 맞음), 랭킹 때문에 생기던 파생물 문제.
- **감수하는 점**: 초기에는 유행 반영이 수동이다(핵심 가치인 "실시간 유행"이 사용자가 모일 때까지 약하다). 네이버 이미지 검색은 일 25,000회 한도를 모든 사용자가 나눠 쓴다. 요금과 광고 수익은 약관 7.2③·7.3④ 때문에 이 API 결과를 쓰는 화면에서는 어렵다(지금은 수익이 필요 없다고 함).
- **확인한 것(이미지 검색 직접 호출, 2026-10-21)**: 네이버 이미지 검색을 "두쫀쿠, 버터떡, 카다이프, 탕후루"로 10장씩 호출했다. 응답에 제목, 크기, 원본 링크, 썸네일이 있다.
  - 두쫀쿠는 거의 전부 관련 사진이었고 네이버 클립 게시물 이미지(세로형)가 많았다. 버터떡은 절반 정도였고 상품 박스와 모형이 섞였다. 카다이프는 재료 상품 사진뿐이었고, 탕후루는 모형·냄비·액자·음원 앨범·이혼 관련 뉴스 사진이 섞여 관련 사진이 3장 정도였다.
  - 검색어에 "디저트"를 붙이면 개선되지 않고 오히려 뉴스·스톡 사진이 늘었다.
  - 원본 링크 중에는 `http://`가 있다. 썸네일은 모두 `https://search.pstatic.net/...` 주소로 와서 우리 사이트(https)에서 쓰기에 안전해 보인다. 다만 썸네일 크기가 주소의 `type=b150`으로 보이는데, 이 크기가 갤러리에 충분한지는 확인하지 않았고 주소를 바꾸는 것은 약관상 확인되지 않았다.
  - 결과를 걸러내거나 가공할 수 없으므로(특약 1.2), 품질은 어떤 디저트를 홈에 올릴지 고르는 것으로 관리한다. 홈에 올릴 디저트는 이미지 결과를 확인한 뒤 고르고, 사용자가 직접 입력한 검색어는 결과를 그대로 보여준다.
- **정한 것(홈 구성과 범위, 2026-10-21)**: (GT) 홈에 올릴 디저트는 미리 DB에 넣어 두고, 접속하면 그중 일부가 랜덤으로 뜬다. 디저트마다 이미지를 열(구역)로 이어서 보여주고, 한 디저트 안의 순서는 API 순서를 유지한다. 운영자 관리 화면은 후순위이고 처음에는 DB에 직접 입력한다. 디저트 저장 기능은 추후 논의 및 개발로 미룬다. 여행지 디저트 찾기는 위치 기반 조회와 지도 이동으로 해결되어 별도 기능을 만들지 않는다.
- **이유(홈 구성)**: (Claude) 이미지는 저장할 수 없어서 방문마다 API를 호출해야 한다. 디저트 카드마다 이미지를 가져오면 호출이 방문당 카드 수만큼 나가 일 25,000회 한도에 빨리 닿는다. 디저트 1~3개의 갤러리를 보여주면 방문당 호출이 1~3번이고, 한 번에 최대 100장을 받을 수 있다. 열로 나누어 이어서 보여주는 방식은 결과의 중간에 다른 내용을 넣지 않는다는 약관 문구에 가깝다고 보았다. 섞은 격자가 약관상 안전한지는 확인하지 못했다.
- **남은 과제**: (1) 검색 한도 대응. 특약 1.4가 허용하는 보관은 기기 24시간과 서버 최대 21일(이력 조회 목적)이라, 여러 사용자가 공유하는 서버 캐시(예: Redis)가 허용되는지는 약관만으로 불분명해서 문의가 필요하다. 한도 증량 가능 여부도 같이 문의한다. (2) 시작용 디저트 목록과 갱신 방식. (3) 사용자 검색어를 어디까지 기록할지(D-02, D-05, 개인정보).

## D-08. 디저트 테이블은 키워드 하나로 둔다 (2026-10-21)

- **정한 것**: 디저트 테이블(`dessert`)은 `id`, `keyword`, `visible`, `created_at` 네 컬럼으로 한다. 화면에 보이는 이름과 네이버에 보낼 검색어를 한 컬럼(`keyword`)으로 합친다. 컬럼 정의는 [요구사항 5.1](./01-requirements.md)에 있다.
- **이유**: (GT) 갤러리는 이미지 중심 화면이라 이름의 중요도가 낮고, 실제로 중요한 것은 사람들이 자주 쓰는 단어와 네이버 검색이 잘 되는 단어인데 이 둘이 같은 단어이기 때문이다.
- **처음 제안과 바뀐 점**: (Claude) 처음에는 화면 이름(`display_name`)과 검색어(`search_query`)를 나눠 제안했다. 검색 품질을 고칠 때 화면 이름이 바뀌지 않게 하려는 이유였으나, 이름이 중요하지 않다면 그 이점이 사라진다. 합치면 구조가 단순해지고, 사용자 검색어와 테이블 값이 같은 종류의 말이 되어 행동 기록의 이름과 바로 비교할 수 있다.
- **나머지 설계 이유**: (Claude) `visible`로 노출만 끄는 것은 행을 지우면 되돌릴 수 없고 행동 기록과 대조할 기준이 사라지기 때문이다. 기본 키는 자동 증가 숫자로 두는데, 이름은 바뀔 수 있어 키로 불안정하기 때문이다. 시간은 서버와 DB의 시간대가 다를 수 있어 시간대 정보가 함께 저장되는 `TIMESTAMPTZ`로 한다. 홈이 무작위로 뽑으므로 정렬 컬럼은 두지 않는다. `UNIQUE`는 같은 키워드가 홈에 두 번 나오는 것을 막는다.
- **다른 선택지**: 화면 이름과 검색어를 나누는 안(위 참고). 나중에 화면에 다른 이름을 보여줘야 하면 비어 있어도 되는 컬럼을 추가하면 되므로 지금은 미리 만들지 않는다.
- **남은 과제**: 시작용 디저트는 [D-12](#d-12-시작용-디저트-10개로-시작하고-화면에서-조정한다-2026-10-21)에서 정했다. 행동 기록 테이블은 [D-09](#d-09-행동-기록-테이블은-네-컬럼으로-하고-원본은-오래-두지-않는다-2026-10-21)에서 정했다.

## D-09. 행동 기록 테이블은 네 컬럼으로 하고, 원본은 오래 두지 않는다 (2026-10-21)

- **정한 것**: 행동 기록 테이블(`search_log`)은 `id`, `device_id`, `keyword`, `time` 네 컬럼으로 한다. 시각 컬럼은 `time`이라는 이름으로 마지막에 둔다. 원본 기록의 보관 기간은 길게 가져가지 않는다. 일정 시점마다 통계 테이블에 모아 두는 방안은 나중에 설계한다. 컬럼 정의는 [요구사항 5.2](./01-requirements.md)에 있다.
- **이유(컬럼)**: (Claude) 항목을 늘릴수록 기기 ID가 다른 정보와 결합될 여지가 커져 개인정보로 판단될 위험이 오르므로 D-05에서 정한 세 항목만 둔다. 기기 ID는 UUID 타입으로 한다(브라우저가 무작위로 만들어 개인을 추측할 수 없고, 문자열보다 공간이 작으며 형식 검증이 된다). `keyword`는 디저트 테이블과 외래 키로 묶지 않는데, 사용자가 목록에 없는 디저트도 검색하기 때문이다. 같은 값의 반복 검색도 신호이므로 `UNIQUE`를 걸지 않는다. 인덱스는 집계가 MVP 밖이라 처음에는 두지 않고, 쓰기 성능과 공간을 아낀다.
- **이유(보관)**: (GT) 원본을 오래 둘 필요가 없고, 나중에 어느 시점부터 통계 테이블을 만들어 저장하는 쪽이 좋겠다.
- **통계 테이블에 대한 Claude의 의견**: 우리가 쌓은 행동 기록을 집계하는 것은 네이버 데이터를 집계하는 것이 아니므로 D-03의 금지와 충돌하지 않는다. 키워드별 일별 검색 횟수처럼 기기 ID가 없는 형태로 모으면 개인정보 부담도 줄어든다. 다만 원본을 지운 뒤에는 다른 기준으로 다시 집계할 수 없으므로, 어떤 기준(키워드, 날짜, 검색한 기기 수 등)으로 모을지 원본을 지우기 전에 정해야 한다. 법률 자문은 아니다.
- **감수하는 점**: `time`은 PostgreSQL에서 컬럼 이름으로 쓸 수 있지만 자료형 이름과 같아 쿼리를 읽을 때 혼동될 수 있다. GT의 결정에 따라 그대로 쓰며, 실제로 불편하면 이름을 바꾼다. 컬럼명은 디저트 테이블의 `created_at`과 방식이 달라 통일성은 떨어진다.
- **남은 과제**: 원본 기록의 보관 기간(숫자), 통계 테이블의 집계 기준과 시작 시점, 안내문의 문구, 개인정보 처리방침이 법적으로 필요한지(D-05).

## D-10. 기본 지도 위치는 강남역으로 한다 (2026-10-21)

- **정한 것**: 위치 권한을 거부했거나 첫 방문일 때 지도는 강남역을 기준으로 연다. 이미지를 눌러 넘어올 때는 해당 가게 위치로 이동한다. 정확한 좌표는 구현 때 정한다.
- **이유**: (GT) 기본 위치로 강남역을 쓰기로 했다. 별도 이유는 기록하지 않았다.
- **참고**: (Claude) 지금까지의 지역 검색 테스트가 모두 강남역 기준이어서(D-06) 이 위치에서는 검색 결과가 어떻게 나오는지 이미 확인된 상태다. 기본 위치는 사용자 위치를 서버로 보내지 않는 NFR-01과 충돌하지 않는다.
- **감수하는 점**: 강남역은 서울 사용자 기준의 기본값이라 서울이 아닌 지역의 사용자가 위치 권한을 거부하면 먼 곳이 보인다. 직접 지도를 옮겨 "이 위치에서 검색"(FR-05)을 쓰면 해결된다.

## D-11. 범위 확장은 동·역 → 구 → 시 순서로 자동으로 하고 알리지 않는다 (2026-10-21)

- **정한 것**: 가게 검색 결과가 0건이면 검색어의 지역을 동·역 → 구 → 시 순서로 넓혀 자동으로 다시 조회한다. 앞 단계에서 결과가 나오면 멈추고, 시 단위에서도 0건이면 결과가 없다고 안내한다. 넓혔다는 사실은 사용자에게 알리지 않는다. 한도 소진 때의 안내 문구는 사용자를 본 뒤에 추가한다.
- **이유(단계)**: (Claude) 네이버 지역 검색에는 반경 파라미터가 없어서 범위를 넓히는 것은 검색어의 지역 이름을 큰 단위로 바꾸는 일이다. 시 단위에서 멈추는 것은 D-06 테스트에서 "서울"까지 넓히면 결과가 흩어지고 관련 없는 곳이 섞였기 때문이다. 0건도 호출 1회로 세므로(NFR-04) 단계를 3개로 제한해 클릭당 최대 3회로 묶는다. 0건만 신호로 쓰는 것은 결과가 있지만 관련이 없는 경우를 걸러낼 방법이 없어서다(특약 1.2~1.3, 걸러내거나 순서를 바꿀 수 없음).
- **이유(알리지 않음)**: (GT) 자동으로 넓히되 알림으로 사용자에게 알릴 필요는 없다.
- **Claude의 의견**: 알리지 않으면 사용자가 "내 주변 결과"라고 오해할 수 있다. 지도가 마커가 모두 보이도록 화면 범위를 맞추므로 멀리 있는 결과라는 것은 지도로 드러난다. 이를 알림 대신 지도 화면이 맡는다고 본다.
- **다른 선택지**: 넓히기 전에 사용자에게 묻는 방식(클릭이 늘고 호출은 줄어듦), 넓힌 단위를 문구로 알리는 방식. 선택하지 않았다.
- **감수하는 점**: 위의 오해 가능성. 사용자를 본 뒤 문제가 보이면 알림을 추가한다. 2·3단계의 구·시 이름은 지도 중심 좌표를 지역명으로 바꿔야 얻을 수 있어서, Reverse Geocoding 방식(D-06 남은 과제)이 정해져야 구현할 수 있다.

## D-12. 시작용 디저트 10개로 시작하고 화면에서 조정한다 (2026-10-21)

- **정한 것**: (GT) 시작용 디저트는 두쫀쿠, 한정선, 피자설기, 고디바 모찌, 아그작, 토라쿠 로얄커스타드 푸딩, 요아정 요거트 찹쌀떡, 크로플, 소금빵, 버터떡 10개로 한다. 키워드의 품질은 화면을 만들어 실제 이미지를 보며 판단하고, 필요하면 키워드를 고치거나 `visible`을 꺼서 뺀다. 이렇게 하는 이유는 키워드가 DB의 한 행이라 바꾸는 비용이 작기 때문이다.
- **이미지 검색 확인(2026-10-21, 키워드별 10장, 제목만으로 판단)**: (Claude) 제목만 본 것이라 실제 사진의 품질은 모른다.
  - 제목이 디저트와 맞아 보인 것: 두쫀쿠(전체 검색 결과 약 10만 건), 피자설기, 고디바 모찌, 버터떡.
  - 상품·판매 이미지가 대부분이었던 것: 크로플, 소금빵(검색 결과가 100만 건 이상으로 많지만 냉동 생지·쇼핑몰 상품 제목이 많았다).
  - 다른 뜻과 섞인 것: 한정선(같은 이름의 가수 뉴스가 10장 중 4장), 아그작(의성어라 책·먹방·뉴스가 섞이고 디저트는 10장 중 3장 정도).
  - 검색 결과가 적거나 어긋난 것: 토라쿠 로얄커스타드 푸딩(전체 153건, 무관한 아이콘 이미지 1장과 같은 제목의 중복이 있음), 요아정 요거트 찹살떡(10장 모두 요아정 브랜드 기사·매장이고 찹쌀떡 상품은 없었다. 입력한 "찹살떡"은 "찹쌀떡"의 오타여서 GT가 확인한 뒤 "찹쌀떡"으로 고쳤다).
- **이유(화면에서 조정)**: (GT) 검증은 의미가 있지만 화면을 만들고 실제 이미지를 보며 테스트하는 것이 맞다. (Claude) 제목만으로는 사진의 품질을 판단할 수 없다는 점에 동의한다. 결과를 걸러낼 수 없는 구조(특약 1.2)에서 품질은 키워드를 고르는 것으로만 관리할 수 있다는 D-07의 판단과도 이어진다.
- **감수하는 점**: 첫 화면에서 품질이 낮은 키워드가 노출될 수 있다. 그럴 때는 해당 행의 `keyword`를 바꾸거나 `visible`을 끈다.

## D-13. 구현은 기존 코드 저장소를 이어 쓰고, 스키마는 V2로 정리한다 (2026-10-21)

- **정한 것**: 코드는 기존 저장소 두 곳을 이어 쓴다. 백엔드는 [trendcanvas](https://github.com/reverieCraftLab/trendcanvas), 프런트는 [trendcanvas-web](https://github.com/reverieCraftLab/trendcanvas-web)이다. 백엔드는 Spring Boot 4.1.0을 유지한다. 이전 설계의 테이블은 Flyway V2에서 정리하고 새 `dessert` 테이블을 만든다. 시작용 디저트 10개는 별도 V3로 넣는다. 구현 순서는 `dessert` 테이블과 홈 API → 네이버 이미지 검색 API → 프런트 → 지도와 가게 검색 → 행동 기록이다.
- **이유(저장소)**: (GT) 코드 저장소가 이미 있어서 요구사항·결정 기록 저장소와 분리해 두고, 구현 중에 정한 내용은 이 저장소에 추가한다. 이 문서는 "무엇을"과 결정 이유를 다루고, 구현 방법(패키지 구조, 엔티티 매핑 등)은 결정 기록에만 둔다.
- **이유(Boot 4.1.0)**: (GT) 스프링은 계속 갱신될 것이므로 최신 안정 버전을 쓰는 것이 맞다. 처음 말한 스택은 3.x였으나 저장소가 4.1.0이어서 의도를 확인한 뒤 유지하기로 했다.
- **이유(V2로 정리)**: (Claude) Flyway는 적용된 파일의 체크섬을 기억하고 내용이 바뀌면 시작 단계에서 막는다. 그래서 V1을 고치지 않고 V2를 덧붙여 "이전 구조 → 새 구조"의 이력을 남긴다. 이전 테이블은 새 설계에서 쓰지 않는다(네이버 결과 저장 안 함, 랭킹 없음, 후보 집계 없음). 스키마(V2)와 초기 데이터(V3)를 나눈 것은 구조 변경 이력과 초기 데이터가 섞이지 않게 하고, 키워드를 나중에 고칠 때 새 마이그레이션 없이 UPDATE로 하기 위해서다.
- **확인한 것**: Supabase의 `trendcanvas` 프로젝트가 일시 중지 상태여서 GT가 다시 켰다. 이전 테이블 4개는 모두 0행이었고 Flyway 이력 테이블은 없었다(V1은 Flyway가 아니라 직접 적용된 것으로 보인다). GT가 이전 테이블 4개를 직접 삭제했다. 그 결과 첫 실행 때 Flyway가 V1부터 V3까지 순서대로 실행해 이력이 정확히 남는다. V1~V3은 임시 PostgreSQL 16에서 순서대로 실행해 문법과 시작 데이터 10행을 확인했다. Supabase에서의 실행은 아직 하지 않았다.
- **RLS(행 수준 보안)**: (Claude) Supabase는 public 스키마의 테이블을 anon 키로도 접근할 수 있게 열어 둔다. 브라우저가 DB에 직접 붙지 않고 Spring만 붙는 구조라서 `dessert`에 RLS를 켜고 정책을 만들지 않았다. Spring이 쓰는 계정이 RLS의 영향을 받지 않는다고 알고 있으나 첫 실행에서 확인한다.
- **감수하는 점**: 무료 Supabase 프로젝트는 일정 기간 사용하지 않으면 일시 중지된다(이번에도 중지되어 있었다). 중지된 동안 서비스가 동작하지 않는다. 대응은 미정이다(NFR-07 위험으로 올릴 예정).
- **남은 과제**: 프런트의 호스팅 위치와 호출 경로(브라우저가 EC2의 Spring을 직접 부를지, Next.js 서버를 거칠지). EC2에 HTTPS가 필요한지는 이 결정에 따라 달라진다. 코드: [6296242](https://github.com/reverieCraftLab/trendcanvas/commit/6296242).

## D-14. 홈 디저트 API는 키워드만 주고, 이미지는 따로 가져온다 (2026-10-21)

- **정한 것**: 홈 API는 `GET /api/desserts/home`이며 노출 중인 디저트에서 무작위로 최대 3개의 번호와 키워드만 내려준다. 이미지는 이 API에서 주지 않고 디저트마다 별도 API에서 가져온다(다음 단계). 이전 설계의 엔티티와 `GET /api/trends`는 코드에서 제거했다.
- **갱신(2026-10-22)**: 홈 디저트 수는 3개에서 5개로, 다시 10개로 바뀌었다([D-17](#d-17-홈-화면은-이미지-중심으로-값을-정했다-2026-10-22)). 코드의 `HOME_LIMIT`은 10이다.
- **이유(키워드만 줌)**: (Claude) 네이버 이미지는 저장하지 않고 요청 시점에 가져와 보여주기로 했다(NFR-05). 홈 API가 이미지까지 모아서 주면 한 요청이 네이버를 최대 3번 부르고 느려지며, 한 디저트가 실패했을 때 홈 전체가 실패한다. 나누면 화면은 키워드를 먼저 받아 영역을 그리고, 각 영역이 이미지를 따로 받아 실패해도 그 영역만 안내하면 된다(NFR-09의 영역별 실패 처리와 맞는다).
- **이유(응답 모양을 DTO로 고정)**: (Claude) 엔티티를 그대로 내리면 DB 구조가 바뀔 때 API 응답도 따라 바뀌어 프런트가 깨진다. `DessertResponse`(번호, 키워드) 하나로 고정해 두었다.
- **이유(무작위 쿼리)**: (Claude) `ORDER BY random() LIMIT n`을 네이티브 쿼리로 쓴다. JPQL에는 표준 무작위 함수가 없고, DB가 PostgreSQL로 정해져 있어(NFR-07) 이식성 문제가 없다. 행이 수십 개 수준이라 느리지 않다.
- **이유(트랜잭션)**: (Claude) 조회 전용 서비스에 `@Transactional(readOnly = true)`를 붙인다. 읽기만 한다는 의도가 코드에 남고, Hibernate가 변경 감지용 스냅샷을 만들지 않는다. `open-in-view`를 꺼 두어 서비스가 끝나면 영속성 컨텍스트가 닫히므로 엔티티를 DTO로 바꾸는 일까지 이 안에서 끝낸다.
- **정한 것(개수)**: (GT) 홈에는 항상 3개를 보여준다. 노출 중인 디저트가 3개보다 적을 때만 있는 만큼 보여준다. FR-01의 "1~3개"를 "3개"로 고쳤다.
- **확인한 것(로컬 PostgreSQL, 2026-10-21)**: GT가 로컬 도커 DB로 앱을 실행해 확인했다. Flyway가 V1~V3를 모두 성공(`success = true`)으로 실행했고, 이전 테이블은 사라지고 `dessert`와 이력 테이블만 남았으며, `dessert`는 10행이었다. `GET /api/desserts/home`은 디저트 3개를 응답했다. 작업 환경에서는 의존성을 받을 수 없어 컴파일을 확인하지 못했으나, GT의 컴퓨터에서 정상 동작했다.
- **확인한 것(Supabase, 2026-10-22)**: GT가 로컬에서 앱을 `prd` 프로파일로 실행해 Supabase에 V1~V3를 적용했다. Supabase를 직접 조회해 Flyway 이력 3건이 모두 성공이고, `public`에 `dessert`와 이력 테이블만 있으며, `dessert`는 10행이고 RLS가 켜져 있는 것을 확인했다. Spring이 쓰는 `postgres` 계정은 RLS를 무시하는 속성(`rolbypassrls`)을 가지고 있고, 공개 키 계정(`anon`, `authenticated`)은 무시하지 않는다는 것을 계정 정보로 확인했다. 따라서 RLS를 켜고 정책을 만들지 않아도 Spring은 읽고 쓸 수 있다.
- **실행 중 만난 문제**: `DB_URL`이 `jdbc:`로 시작하지 않아 시작 단계에서 오류가 났다(접속 전이라 비밀번호 시도는 없었다). 값을 `jdbc:postgresql://호스트:5432/postgres?sslmode=require` 형태로 고쳐 해결했다. 코드: [trendcanvas 저장소](https://github.com/reverieCraftLab/trendcanvas)의 `dessert` 패키지.

## D-15. 이미지 API는 서버가 네이버를 호출해 그대로 돌려준다 (2026-10-22)

- **정한 것**: `GET /api/images?keyword=두쫀쿠&start=1`이 키워드 하나를 받아 서버가 네이버 이미지 검색을 호출하고 응답을 가공 없이 돌려준다. 홈에서는 디저트 구역마다 이 API를 동시에 따로 부르고(GT 결정), 스크롤 추가 로드와 사용자 검색(FR-03)도 같은 API를 쓴다. `display`는 서버가 100으로 고정한다. 한도 초과(네이버 429)는 HTTP 503과 `QUOTA_EXCEEDED`로, 그 밖의 실패는 502와 `UPSTREAM_ERROR`로 돌려준다. 코드 위치는 [D-16](#d-16-패키지는-기능별로-나누고-그-안을-계층-폴더로-다시-나눈다-2026-10-22)을 따른다.
- **갱신(2026-10-22)**: `display` 고정값은 100에서 10으로 바뀌었고, 검색어 뒤에 ` 디저트`를 붙였다가 다시 뺐다([D-17](#d-17-홈-화면은-이미지-중심으로-값을-정했다-2026-10-22)). 아래 "display 100 고정" 이유는 처음 결정의 근거이고, 바뀐 이유는 D-17에 있다.
- **이유(홈 API와 분리)**: (GT, Claude 정리) 흐름은 "접속 → 비동기로 백엔드 호출 → 백엔드가 네이버를 REST로 호출 → 프런트 전달"이다. 홈 API(D-14)는 키워드만 주고 이미지는 이 API가 주는 이유는 스크롤 추가 로드가 어차피 디저트별·`start`별 이미지 API를 필요로 하기 때문이다. 이미지를 홈 API에 같이 넣으면 같은 기능이 두 곳에 생기고, 한 디저트가 실패했을 때 홈 전체가 실패한다. 나누면 실패가 그 구역에만 영향을 준다(NFR-09).
- **이유(display 100 고정)**: (Claude) 네이버는 `display`와 무관하게 요청 1건을 1회로 세므로(NFR-04 측정) 한 번에 최대치를 받는 것이 같은 이미지를 보여줄 때 호출이 가장 적다. 값을 고정해 사용자가 한도를 소모하는 입력을 바꾸지 못하게 한다.
- **이유(입력 검증)**: (Claude) 네이버는 잘못된 요청도 호출 1회로 세므로 검색어(필수, 100자 이내)와 `start`(1~1000)를 네이버로 보내기 전에 컨트롤러에서 검증한다. `start` 최대 1000은 네이버 문서 기준으로 알고 있는 값이며 직접 호출해 확인하지는 않았다.
- **이유(429를 따로 다룸, 재시도 없음)**: (Claude) 한도가 찬 상태의 재시도는 성공하지 않고 호출만 늘린다(NFR-04, 약관 7.3⑫). 프런트가 한도 소진과 일반 실패에 다른 안내를 보여줄 수 있도록 코드로 구분한다. 오류 응답에 네이버 응답이나 키는 넣지 않는다.
- **이유(시간 제한)**: (Claude) 연결 2초, 응답 3초 제한을 둔다. 제한이 없으면 네이버가 느릴 때 요청이 쌓여 t2.micro의 스레드가 묶일 수 있다. 숫자는 NFR-08(첫 이미지 2.5초)과 네이버 응답 시간 측정(0.15~0.26초)을 보고 정한 초기값이며 EC2에서 측정한 뒤 조정한다.
- **이유(트랜잭션 없음)**: (Claude) 이 서비스는 DB를 쓰지 않는다. 트랜잭션은 DB 연결을 잡고 있는 구간을 정하는 도구인데, 외부 API를 부르는 동안 연결을 잡고 있으면 네이버가 느릴 때 연결만 낭비된다. 행동 기록 저장 같은 DB 작업은 이 호출과 분리해 짧은 트랜잭션으로 따로 처리한다.
- **이유(키 처리)**: (Claude) 키는 환경 변수(`NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`)에서만 읽고 호출 클라이언트를 만들 때 기본 헤더로 한 번만 등록한다(NFR-06). 키가 없어도 앱은 켜지고, 이미지를 부르는 시점에 분명한 오류가 난다.
- **코드**: [094c182](https://github.com/reverieCraftLab/trendcanvas/commit/094c182) (이미지 API 추가와 기능별 폴더 구조 정리, `application.yaml` 삭제 포함).
- **프런트에 남기는 조건**: 네이버 `title`에는 `<b>` 같은 HTML 태그가 섞여 있다. 서버는 가공하지 않으므로(NFR-05) 프런트는 이 값을 HTML로 해석하지 말고 글자로만 표시해야 한다(XSS 방지).
- **설정 정리**: (GT) 중복이던 `application.yaml`을 삭제하고 `application.yml`로 합쳤다. 네이버 설정은 `application.yml`에 있다.
- **응답을 문자열로 받아 직접 읽는 이유**: (Claude) 처음에는 응답을 `NaverImageResponse`로 바로 받게 했으나, 네이버(API HUB)가 JSON 내용을 `Content-Type: text/plain`으로 보내서 "변환기를 찾을 수 없다"는 오류가 났다. Spring의 JSON 변환기는 `application/json`일 때만 동작하기 때문이다. 그래서 응답을 문자열로 받은 뒤 Jackson 3(Spring Boot 4가 쓰는 `tools.jackson`)으로 직접 읽는다. 값은 가공하지 않는다. 외부 API는 문서나 예상과 다른 헤더를 줄 수 있고 실제 호출을 해 봐야 드러나므로, 연동할 때는 컴파일과 시작 확인에 더해 실제 응답 한 번을 확인한다.
- **로그**: (Claude) 네이버 호출 실패와 서버 설정 오류(키 미설정 등)는 사용자에게 원인을 알리지 않고 서버 로그에만 남긴다. 처음에는 로그가 없어 500의 원인을 찾기 어려웠다. 로그에도 키와 네이버 응답 본문은 넣지 않는다.
- **확인한 것(2026-10-22)**: Gradle 컴파일이 통과했고, GT가 로컬에서 앱을 실행해 `GET /api/images?keyword=두쫀쿠&start=1`이 네이버의 실제 응답(`total` 102,712건, 한 번에 100장)을 그대로 돌려주는 것을 확인했다. 잘못된 입력(`start=0`, 빈 키워드)은 400으로 막히고 네이버를 호출하지 않았다. 한도 초과(503)와 일반 실패(502) 응답을 실제로 일으켜 확인하지는 않았다.
- **프런트에 남기는 조건(추가)**: 응답의 `link`(원본 이미지 주소)는 `http://`로 올 수 있다. 우리 사이트는 HTTPS이므로 `<img>`에는 `https://search.pstatic.net/…`로 오는 `thumbnail`을 쓰고, `link`는 원본 링크 표기 용도로만 쓴다(NFR-05의 출처·원본 링크 표시).
- **남은 과제**: 브라우저가 이 API를 부를 때의 CORS와 호출 경로(Vercel에서 EC2의 Spring을 직접 부르면 EC2에 HTTPS가 필요하고 도메인과 인증서를 붙여야 한다), 행동 기록(FR-08)과의 연결.

## D-16. 패키지는 기능별로 나누고, 그 안을 계층 폴더로 다시 나눈다 (2026-10-22)

- **정한 것**: 백엔드(`trendcanvas`)는 기능마다 폴더를 만들고(`dessert`, `image`, `naver`), 그 안에 `controller`, `service`, `repository`, `domain`(엔티티), `dto`, `client`(외부 API 호출), `config`, `exception` 같은 계층 폴더를 두어 파일을 넣는다. 파일 이름에 종류를 붙이는 관습(`...Controller`, `...Service`)은 그대로 쓴다. 한 기능에 속하지 않는 공통 오류 처리(`ApiExceptionHandler`)는 `common/exception`에 둔다.
- **이유**: (GT) 회사에서 쓰던 방식, 즉 폴더를 나누고 그 안에서 컨트롤러·서비스·VO·매퍼를 종류별 폴더로 관리하고 파일 이름에 종류를 붙이는 방식이 더 익숙하고 읽기 편하다. 기능별 폴더 아래에 계층 폴더를 다시 두는 구조로 정리했다.
- **과정**: (Claude) 처음에는 "회사 방식"을 폴더 전체를 계층별로만 나누는 구조(`controller/`, `service/`가 최상위)로 해석해 그렇게 옮겼다. GT가 기능별 폴더 아래에 계층 폴더를 두는 구조라고 바로잡아 다시 옮겼다. 두 번 모두 `git mv`로 옮겨 이력은 이어진다.
- **회사 구조와의 대응**: Controller, Service는 같은 개념이다. Mapper(MyBatis)의 자리는 JPA에서 Repository가 맡는다. VO의 자리는 응답 전용 DTO(`record`)가 맡는다. 마이크로서비스(MSA)가 아니라 하나의 프로그램 안에서 폴더만 나눈 것이다.
- **다른 선택지**: 최상위를 계층별로만 나누는 구조(`controller/`, `service/`, …). 기능이 적을 때는 단순하지만 기능이 늘면 한 폴더에 파일이 쌓인다. 선택하지 않았다.
- **감수하는 점**: 경로가 깊어진다(예: `naver/exception/…`). 여러 기능이 같이 쓰는 코드는 어느 기능 폴더에 둘지 애매하고, 지금은 `common`에 둔다. 외부 호출(`naver`)은 기능이라기보다 연동 모듈에 가깝지만 같은 규칙으로 다뤘다.
- **확인한 것**: Gradle 컴파일이 통과했다. 앱을 다시 시작해 동작을 확인하는 것은 GT가 한다.
- **함께 배운 것(의존성 주입)**: 첫 구현에서 `NaverImageClient`가 `RestClient.Builder`를 주입받도록 썼는데 Spring Boot 4에서는 그 빈이 기본으로 만들어지지 않아 시작할 때 실패했다. `RestClient.builder()`로 직접 만들도록 고쳤다. 빈의 존재는 컴파일이 아니라 앱 시작 때 확인되므로, 새 클래스를 추가하면 컴파일 통과만으로 끝내지 않고 앱을 띄워 확인한다.

## D-18. 행동 기록은 PostgreSQL에 그대로 쌓고, 시계열 DB는 쓰지 않는다 (2026-10-24)

- **정한 것**: `search_log`는 지금처럼 Supabase의 PostgreSQL에 쌓는다. 시계열 전용 DB는 쓰지 않는다. 컬럼과 인덱스 방침은 [D-09](#d-09-행동-기록-테이블은-네-컬럼으로-하고-원본은-오래-두지-않는다-2026-10-21)를 그대로 따른다.
- **배경**: (GT) 사용자가 늘면 검색 순위를 집계할 수 있겠다고 보았고, 로그를 쌓을 때는 시계열 DB가 좋다고 들은 적이 있어 물었다.
- **이유(쓰기량)**: (Claude) 로그는 사용자가 검색할 때마다 한 줄씩 쌓이고, 이미지를 더 불러오는 스크롤은 쌓이지 않는다. 네이버 검색 한도가 하루 25,000회(NFR-04)라서 검색 기록이 하루에 많아야 수만 건이라고 추정했다. 초당 1건이 안 되는 양이라 PostgreSQL로 충분하다고 판단했다. 이 숫자는 측정값이 아니라 추정이다. 시계열 DB는 초당 수천 건 이상처럼 쓰기가 훨씬 많을 때 이점이 크다.
- **이유(운영)**: (Claude) 별도 DB를 두면 서버가 하나 더 필요하다. 지금은 EC2 t2.micro와 Supabase만 쓰고 있어서 메모리와 운영 부담이 늘어난다. 로그만 다른 저장소에 두면 `dessert` 테이블과 함께 조회하기도 어려워지고, 이미 쓰는 JPA와 Flyway 방식과도 맞지 않는다.
- **다른 선택지**: 시계열 전용 DB(TimescaleDB, InfluxDB 등). 선택하지 않았다. 규모가 커졌을 때 다시 검토한다.
- **나중에 쓸 수 있는 방법(채택한 것은 아니다)**: 집계가 필요해지면 `time` 컬럼에 BRIN 인덱스를 둔다(시간 순서로 쌓이는 로그에서 작고 효율적). 데이터가 커지면 월 단위로 파티션을 나눈다. 화면은 원본을 매번 훑지 않고 일별 요약 테이블을 읽는다. 요약 테이블은 D-09에서 이미 정한 "원본을 오래 두지 않고 통계 테이블에 모으는" 방향과 같다.
- **다시 검토할 시점**: 로그가 수천만 건을 넘어 집계가 눈에 띄게 느려질 때, 또는 실시간 대시보드가 필요해질 때.
- **감수하는 점**: 규모가 매우 커지면 PostgreSQL 안에서의 튜닝만으로는 한계가 올 수 있다. 그때는 저장소를 옮기는 작업이 생긴다.
- **남은 과제**: 통계 테이블의 집계 기준은 D-09에서 미정으로 남아 있다. (Claude) 후보 기준 두 가지를 적어 둔다. 하나는 단순 검색 횟수보다 "최근 며칠간의 증가 속도"가 유행 초기를 더 빨리 보여줄 수 있다는 점이다. 다른 하나는 한 사람이 같은 디저트를 여러 번 검색해도 순위가 움직이지 않도록 기기당 하루 1회처럼 중복을 제거하는 기준이 필요할 수 있다는 점이다. 둘 다 원본을 지우기 전에 정해야 하며, 아직 정한 것은 아니다.


## D-19. 백엔드는 EC2 한 대에 nginx와 systemd로 배포한다 (2026-10-25)

- **정한 것**:
  - 서버는 서울 리전의 EC2 한 대(t3.micro, Ubuntu 24.04, vCPU 2·메모리 1GB)다. 고정 주소는 **탄력적 IP**로 붙인다.
  - 백엔드 주소는 `https://api.trendcanvas.reveriecraftlab.com`이다. 가비아에서 A 레코드 하나(`api.trendcanvas` → 탄력적 IP)를 둔다.
  - 80·443은 **nginx**가 받고 안쪽의 `127.0.0.1:8080`(Spring Boot)으로 넘긴다(리버스 프록시). 8080은 보안 그룹에서 열지 않는다. HTTPS 인증서는 Let's Encrypt(certbot)로 받고 자동 갱신한다. HTTP는 HTTPS로 리다이렉트(301)한다.
  - 앱은 `systemd` 서비스(`trendcanvas`)로 실행한다. 권한이 없는 전용 사용자(`trendcanvas`, 로그인 불가)로 돌리고, 실패하면 5초 뒤 다시 시작하며, 서버가 켜지면 자동으로 시작한다. JVM은 `-Xms256m -Xmx512m`로 제한한다.
  - 서버에 **스왑 2GB**를 둔다(`/etc/fstab`에 등록).
  - 비밀 값(DB 접속 정보, 네이버 키)은 서버의 `/etc/trendcanvas.env`(소유자 root, 권한 600)에 두고 systemd가 앱에 환경 변수로 넘긴다. 코드, 설정 파일, 문서에는 값을 적지 않는다. 같은 파일에 `SPRING_PROFILES_ACTIVE=prd`와 `CORS_ALLOWED_ORIGINS`(프런트 주소, D-17)도 둔다.
  - 배포는 **내 컴퓨터에서 `./gradlew bootJar`로 만든 jar를 `scp`로 올리는 수동 방식**이다. 서버에는 `/opt/trendcanvas/app.jar`로 둔다.
  - SSH(22)는 내 IP에서만 받고, 로그인은 키 파일로만 한다. 키 파일은 저장소 밖에 둔다.
- **이유(nginx를 앞에 둠)**: (Claude) 브라우저는 HTTPS 페이지에서 HTTP API를 부르는 것을 막는다(혼합 콘텐츠). 프런트가 HTTPS라서 API도 HTTPS여야 한다. 인증서 처리와 80/443 수신을 nginx가 맡으면 Spring은 인증서를 몰라도 되고, 앱은 외부에 직접 노출되지 않는다.
- **이유(전용 사용자와 환경 변수 파일)**: (Claude) 앱에 취약점이 생겨도 서버 전체 권한이 넘어가지 않게 하려고 로그인이 불가능한 최소 권한 사용자로 돌린다. 비밀번호와 키는 root만 읽는 파일에 두고 systemd가 읽어 앱에 전달하므로, 앱 사용자가 파일을 직접 읽을 필요가 없다.
- **이유(스왑과 힙 제한)**: (Claude) 메모리가 1GB뿐이라 순간적으로 몰리면 리눅스가 JVM을 강제로 종료한다. 스왑은 그때 디스크를 임시 메모리로 써서 프로세스가 죽지 않게 하는 안전장치이고, 힙 512MB 제한은 nginx와 운영체제가 쓸 메모리를 남기기 위한 것이다. 배포 직후 앱은 약 225MB를 썼고 스왑은 쓰지 않았다.
- **이유(수동 배포)**: (Claude) 서버에서 Gradle로 빌드하면 메모리 부족으로 실패하는 경우가 많아 jar만 올린다. 처음에는 직접 해 봐야 각 단계를 이해하므로 자동화(GitHub Actions 등)는 수동 방식이 한 번 돌아간 뒤로 미룬다.
- **이유(t3.micro)**: (GT) 인스턴스 선택 화면에서 t2.micro가 보이지 않아 t3.micro로 만들었다. (Claude) 둘은 같은 사양(vCPU 2, 메모리 1GB)이라 설치와 설정이 같다. NFR-07의 인스턴스 이름은 이에 맞춰 고쳤다.
- **이유(리전)**: (Claude) 사용자가 한국에 있으므로 서울로 둔다. 처음 다른 리전에 만들었다가 서울로 다시 만들었다. 지연을 줄이고, 이미지 API는 서버가 네이버를 호출하는 구조라서 서버가 가까울수록 응답이 빠르다.
- **다른 선택지**: 프런트 서버(Next.js)를 거쳐 API를 부르는 방식(경로 B)은 D-17에서 쓰지 않기로 했다. 서버에서 Docker로 실행하는 방식은 메모리 부담을 줄이려고 쓰지 않았다.
- **확인한 것**(2026-10-25): 서버에서 앱이 `prd` 프로파일로 시작해 Supabase에 접속하고 Flyway·JPA 검증을 통과했다. 시작 시간 약 10초. `GET /api/desserts/home`이 서버 안과 `https://api.trendcanvas.reveriecraftlab.com`에서 디저트 10개를 반환했다. 한글 검색어는 URL 인코딩해서 보내야 한다(`curl`은 `--data-urlencode`). 인코딩하지 않으면 Tomcat이 400을 돌려주며, 브라우저는 자동으로 인코딩하므로 서비스에는 영향이 없다. `GET /api/images?keyword=소금빵`이 서버에서 네이버를 호출해 `total`·`items`를 그대로 반환했다. HTTP 요청은 301로 HTTPS로 넘어가고, 인증서 갱신 모의 실행(`certbot renew --dry-run`)이 성공했다.
- **확인한 것(재부팅, 2026-10-25)**: 서버를 재부팅한 뒤 `trendcanvas` 서비스가 사람이 시작하지 않아도 `active (running)`으로 올라왔다(부팅 후 약 15초에 시작, 앱 시작 12초). 이때 서비스 메모리는 373MB(최대 382MB), 서버 전체 메모리 사용률 58%, 스왑 사용 0%였다.
- **확인한 것(8080, 2026-10-25)**: 외부(내 컴퓨터)에서 `http://<서버 IP>:8080`을 부르면 5초 뒤 시간 초과(`curl` 종료코드 28)로 응답이 없다. 앱은 nginx를 통해서만 접근된다.
- **확인하지 않은 것**: 실제 프런트 주소에서 CORS 호출이 통과하는지, EC2에서의 첫 이미지 응답 시간(NFR-08)과 서버 메모리 변화.
- **감수하는 점**:
  - 수동 배포라 배포할 때마다 jar를 만들어 올리고 서비스를 다시 시작해야 한다. 그 사이 몇 초는 응답이 끊긴다.
  - 서버가 한 대라 서버나 nginx가 죽으면 서비스 전체가 멈춘다.
  - nginx 접속 기록에는 방문자 IP가 남는다. 앱은 IP를 저장하지 않는다는 설계(NFR-01 계열)와 어긋나지 않는지 보관 기간과 안내문을 함께 정해야 한다.
  - 메모리 1GB라 앱이 늘면 스왑 사용이 늘고 느려질 수 있다.
- **남은 과제**: 프런트 배포(주소 `trendcanvas.reveriecraftlab.com`)와 실제 CORS 확인, nginx 접속 기록의 IP 보관 기간, 배포 자동화 여부, Supabase 일시 중지 대응.
